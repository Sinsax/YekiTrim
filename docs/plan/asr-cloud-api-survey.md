# ASR 方案探索：云端 API 供应商

> **状态：纯调研，未改任何代码。**
> 上游：`asr-model-landscape-survey.md`（本地模型）、`asr-per-mode-tradeoff-survey.md`（单/双模型）。
> 日期：2026-07

## 0. 先说结论：**技术上可行，但与 V-Trim 的部署契约冲突**

云端 ASR **能解决精度问题**（商业 API 的 CER 已与开源 SOTA 同级甚至更好），
但它**打破 V-Trim 三条既有契约**：

| # | 契约 | 现状 | 上云后 |
|---|---|---|---|
| **D1** | **离线可用** | `docs/deploy.md` 的 A/B/C 三种部署形态都假定**本地推理**；模型随 `vtrim download` 落盘（`models/` ~1.1 GB） | 转写**必须联网**；无网 = 核心功能失效 |
| **D2** | **密钥归用户** | `llm.toml` 的 `base_url` + `api_key` 是**用户自己填的**，项目不代收分文 | 两种可能：用户自带 key（同 LLM 形态），或项目方代付（**变成计费/合规主体**） |
| **D3** | **音频不出机器** | 录播视频**全程留在用户本地** | **3 小时录播要上传给第三方** —— 隐私面彻底改变 |

⭐ **D3 是最重的一条**。V-Trim 处理的是**直播录像**（可能含未公开内容、观众声音、主播隐私），
`--allow-remote` 那套公网部署纪律（`docs/deploy.md` C 节）管的是"谁访问服务"，
而云端 ASR 引入的是**"你的音频要交给谁"** —— 这是**全新的信任面**，现有部署文档没有覆盖。

## 2. ⚠️ 关键技术陷阱：**默认时间戳是句级，不是逐字**

这是本次调研**最有价值的发现**。V-Trim 要的是**逐字（character-level）**时间戳
（`CharTimeline` 靠**相邻字**时间差找气口，见 `align.rs:107-123`），而云端 API 的**默认**粒度是**句级**：

- **阿里云**：默认返回 `Sentences`（句级 `BeginTime`/`EndTime`）；
  **要词级必须显式开** `version=4.0` + `enable_words`，读 `Words` 数组。
  官方 FAQ 还专门列了"**录音文件识别时间戳不准**"这一条，解法是 `enable_timestamp_alignment=true`。
- **讯飞**：词级时间戳**要显式开 `has_participle=true`**，且是**"词"**（`wordsName`）——
  中文分词后**一个"词"通常 1~3 个字**，⚠️ **这正是 Dolphin 那种"多字共用一个时间戳"的粒度问题**。
  它还有个 `eng_vad_margin` 参数（"不带静音信息可以使得词相对于本句子的起始帧更精确"），
  说明**时间戳精度是需要调的旋钮**，不是白给的。
- **阿里云**甚至有个反直觉的坑：*"如果是 vad 断句情况下，实时转写的 vad 断句依赖对音频中静音数据的判断"* ——
  音频里的静音处理会直接影响时间戳。

**结论**：**即使开了词级，中文的"词级"也≠"逐字"**。V-Trim 的 `CharTimeline::from_tokens`
（`align.rs:77-91`）虽然能把多字 token 摊成单字、共享时间戳，但**气口粒度会退化**
（一个三字词内部检测不到停顿）—— 这与 Dolphin 被否掉是**同一个理由**。

⚠️ **阿里云的"字级"是否真的做到单字，需要实测确认**：它的字段名是 `Words`（词），
中文分词后可能仍是多字词。**这是上云前必须先验证的第一件事。**

## 3. 成本与延迟

| 维度 | 本地（现状） | 云端 |
|---|---|---|
| 3 小时录播耗时 | single **83.7 s**；hybrid **~15 min** | 讯飞：60 分钟以上音频 → **10~20 分钟**（含排队） |
| 边际成本 | **0**（已买硬件） | 按分钟计费，**每场录播都花钱** |
| 突发/排队 | 无 | ⚠️ 讯飞明写"**忙时会出现任务排队**"，SLA 最长 5 小时 |
| 隐私 | 音频不出机器 | **音频上传第三方** |

⚠️ V-Trim 是**直播录像切片工具**，若做成多租户 SaaS，
**按分钟计费的成本会直接落到项目方头上**（除非走"用户自带 key"）。

## 4. 可行性与建议

### 4.1 唯一合理的形态：**用户自带 key 的可选后端**

即在 `[asr]` 里新增一个 `cloud` 模式，配置形如：

```toml
[asr]
mode = "cloud"          # 新增
[asr.cloud]
provider = "aliyun"     # aliyun | tencent | xfyun | openai ...
api_key = ""
```

这与 **`llm.toml` 的既有形态完全一致**（`base_url` + `api_key` 由用户填），
**不引入计费主体、不引入项目方合规责任**。这是唯一与现有架构不冲突的做法。

### 4.2 但不建议作为默认/主力

1. ⚠️ **D3 隐私面是硬伤**：录播内容上传第三方，需要在界面上**明确告知并让用户确认**，
   而 V-Trim 现在的产品定位是"本地工具"。
2. ⚠️ **逐字时间戳仍不保证**：§2 已说明，云端给的多是**词级**（中文分词后 1~3 字），
   **气口粒度会退化** —— 这与本地模型的可控性相比是**降级**。
3. ⚠️ **离线形态被打破**：`docs/deploy.md` 的 A 档（纯本地）将不再成立。

### 4.3 真正值得考虑的场景

| 场景 | 是否推荐 |
|---|---|
| 用户对精度要求极高、且**不介意上传** | ⭐ 可行（自带 key） |
| 本地机器太弱（跑不动 qwen3） | ⭐ 可行 —— **这是云端最有说服力的理由** |
| 方言/小语种（讯飞可买方言包） | ⭐ 可行 |
| 默认链路 / 多租户 SaaS 的公共额度 | ⛔ **不建议**（成本 + 隐私） |
| 敏感内容的录播 | ⛔ **绝不** |

## 5. 如果要做，第一步必须验证什么

1. ⭐ **拿一段真实录播，开词级时间戳，把返回的时间戳与 V-Trim 的 `CharTimeline` 对一遍** ——
   **确认是不是真的到了"单字"粒度**，还是"词"（多字共享一个时间戳）。
   **这一条不通过，后面都不用谈。**
2. **确认时间戳在 BGM/唱歌段的行为**（与本地 firered 那个幽灵戳问题是同一类风险）。
3. 确认**成本模型**（每场录播多少钱）与**排队延迟**在可接受范围。
4. 确认**上传带宽**：3 小时录播的音频（16k mono WAV ≈ 345 MB；转成 opus 可降到 ~30 MB）
   —— 建议**先转码再上传**，否则上传本身就是瓶颈。
