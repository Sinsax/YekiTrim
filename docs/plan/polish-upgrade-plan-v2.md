## 7. 验收总纲（**用户定的硬标准**）

> **每一项都必须有「真机可见」证据，否则不算完成。**

| 类别 | 可接受的证据 |
|---|---|
| 画面类 | **出片截图 / 逐像素测量 / 同帧预览 vs 成片对比** |
| 界面类 | **界面截图**（控件真的在、真的能点） |
| 音频类 | **响度测量**（如 BGM 闪避 −43.9 → −34.7dB） |
| 门禁类 | **变异自证**（改回旧行为 ⇒ 必须红） |

⚠️ **"判据绿"本身不是证据** —— 本轮问题的根因就是"判据全绿、产品没变"。
⚠️ **"代码在"更不是证据** —— 那正是 §18-A 的坑。

### ★ 本轮实测得出的三条方法论（**必须遵守**）

**① 先验量具，再用量具。**
批 2 的 §20 证据工具在**上真工程之前**先拿合成夹具验了**工具本身**，结果发现：
我批准的"方差"判据**几乎分不开**它要分的东西 ——

```
  方差      A=920.46  B=1106.12   B/A=1.20x   ← 弱信号，被画面自身 ~920 的方差淹没
  高频能量  A= 0.7598 B=  6.3568  B/A=8.37x   ← 真分界（白纱=低频常数位移 / 噪声=逐像素颗粒）
```
⇒ **判据本身也是被测对象。** 没这一步，交出来的是"看起来有数字、其实没有判别力"的东西。

**② 死判据有**两个**方向**：永远绿（摆设）和**永远红（空转）。
本轮两种都抓到过：4 次"变异该红没红" + 1 次"判据要求的东西与设计相反、注定永远红"。
⇒ 写完判据要问两句：**它红得了吗？它绿得了吗？**

**②b 与"假失败"对称的第三个坑：变异本身没打上。**
§20 那条线上，变异正则**打不中真实调用**（它嵌在模板串里：`url(${noiseTile(…)})`）
⇒ 变异**静默 no-op**，却被报成"判据没翻面"。
★ 后果**与假成功相反**：
- **假成功**：变异没打上、判据本来红 ⇒ **以为判据有效**
- **假失败**：变异没打上、判据当然不翻面 ⇒ **以为判据无效** ⇒ 可能把一个**好判据**改坏
⇒ 落法（已采用）：`expectRed` 要**自证变异真的改动了文本**，替换前后相同就报
「**变异没打上（正则写错了）**」，**不与"判据没翻面"混为一谈**。

**②c 黑名单堵不完，白名单才能完成证明。**
原帧号判据用**反向**写法（"不许 `* fps`"）⇒ `current * 30`（**数字字面量**）能溜过去。
⇒ 改成**白名单**：实参必须**恰好等于** `dhampirFrameShown` ⇒
`current*30` / `current*srcFps` / `Math.round(t*60)` / `dhampirFrameShown+1` **四种全部翻面**。
本轮两种都抓到过：4 次"变异该红没红" + 1 次"判据要求的东西与设计相反、注定永远红"。
⇒ 写完判据要问两句：**它红得了吗？它绿得了吗？**

**②d grep 作为验收手段，两个方向都会骗你**
- **"grep 不到 ≠ 没打进去"**：打包会**改名**（压缩）、会**换文件类型**
  （Vue scoped CSS 编进 `.css` 而非 `.js`）⇒ 要查**行为特征**（`toDataURL`/`overlay`）。
- **"grep 到了 ≠ 就是那样"**：**注释里为讲清历史会引用旧写法** ⇒
  一条"这里曾经读 `e.kind`"的注释，会让 grep 判据以为代码没改。
⇒ **grep 命中既非充分也非必要。** 这也是"喂真事件、跑真求值器"式判据存在的理由。

**②e 误报与漏报同等有害 —— 判据要设在"最终可见结果"上。**
§20 线上，两腿的噪声不透明度峰值显示为 **0.972（成片）vs 0.078（预览）**，
看着像**12.5 倍分叉**。查清后是**等价编码**：

| 腿 | 图层不透明度 | 噪声强度 | 合成 |
|---|---|---|---|
| 成片 | **包络本身**(峰值 0.972) | `params.amount = 0.08` | 0.972 × 0.08 |
| 预览 | **包络 × amount**(峰值 0.078) | 写死在贴图里(全强度) | 0.078 × 1.0 |

**逐帧验证**：预览值 **精确等于** `包络 × 0.08`（差 ~1e-7，浮点精度内）⇒ **最终强度相同**。

★ **若直接报"0.972 vs 0.078"就是误报** —— 而且会**引导别人去修一个本来是对的地方**。
⇒ **误报与漏报同等有害**：漏报 = 坏了没人知道；**误报 = 好的被人"修"坏**。
⇒ **一般化**：**两个不同的中间表示、最终语义相同 ⇒ "数值不同"本身不是判据。**
**判据必须设在"合成之后的可观测量"上**（本轮即：真机同帧画面的**高频能量**）。

**②f 「命令跑成功」≠「命令做了那件事」。**
§18-A 取样时我跑的是 `polish process` 而不是 `polish llm` —— 前者**不调 LLM**，
只是把已有的 `polish.toml` 重新规范化。于是三次"结果"是 `特写=0/0/0`，看着像 FAIL。

★ **识破它的是三个旁证**：① **耗时 1s**（真 LLM 采样不可能）② 三次 zoom 分布**完全相同**
（真采样不可能）③ 重跑后文件 md5 只有 2 个值。
⇒ **`exit 0` + 产物存在 + 数值合理，三个都对，而整件事是错的。**
**教训**：交付负数结果（"修了没用"）前，**先自问"我真的调用了那个被修的东西吗"**。
假 FAIL 与假 PASS 一样有害 —— **它会让人去改一个已经修好的地方**。

**③ 判据必须容忍"合法的不一致"。**
GPU 底座 vs 浏览器 CSS **本来就不逐像素相同**。§20 的度量用
**「成片另一帧号的噪声 vs 预览」= 0.99x** 证明了自己**不会**把合法差异误判成不一致 ——
这正是它**不会变成永远红**的原因。⇒ 硬要求逐像素相等只会得到一个假判据。

## ✅ W1 已修（P0，跨仓 Dhampir `020a2da`）：`noise` 把画面整个洗掉

> ⚠️ 本节原来标的是"🔴 未修"。**根因不是观感、也不是 YekiTrim 的问题，是 Dhampir 的一个 255 倍量纲错误。**

**根因**：`67ba95c` 加了 `const NOISE_FULL_SCALE: f32 = 255.0`，理由是
"`textureLoad`（`Rgba8Unorm`）出来是 0..255"。**`Unorm` 的 `textureLoad` 返回 0.0..1.0**，
不是裸的 0..255 ⇒ 噪声被放大 255 倍、淹没画面。

**同一个着色器里的反证**：第 1 段 `mix(rgb, flash_color, flash_amount)` 的 `flash_color`
来自 `param("r").unwrap_or(1.0)`（Rust 侧 `clamp(0.0,1.0)`）；若 `rgb` 真是 0..255，
这一混会把画面压成 1/255 的黑。**实测 flash 亮度正常**（122.04 → 140.65）⇒ `rgb` 是 0..1。

### ★★ 本次最值钱的一条教训：**"超过理论上界"的读数 = 上界算错了的告警**

`67ba95c` **自己记下过一条对不上的读数**：
> "`amount=0.08` 时实测到 `+171` 的跳变，**超过了单趟满幅上界 10.2**……
>  剩下的嫌疑是调整层那趟的 `strength` 折算，**我没跟到底**"

它甚至把断言从 `127.5` **放宽到 255** 来容纳这个异常。
**但 `10.2` 是"在 0..255 空间"算的上界，而 `+171` 是"在 0..1 空间"量到的 ——
两个空间差 255 倍，与那个错误常量严丝合缝。**
⇒ **测试看见了 bug，把它记成"未知异常"，然后放宽了判据。**

**两条纪律**：
1. **一条"超过理论上界"的读数，第一嫌疑是上界（量纲），不是实现。**
2. **放宽任何阈值时必须写下"放宽后该触发什么后续动作"** —— 当年那条注释其实很诚实
   （"这是承认没查清、不是它没问题"），但**没有触发任何动作**，于是静静躺了两个月。

⚠️ 还有一条**与 W1 无关的独立缺陷曾混在一起**：`noise` 一度"挂上/不挂逐字节相同"，
  那是**调整层整层没跑到**（`is_adjustment` 未置位）—— 已由 Dhampir 的噪声用例钉住。
  ⇒ **两个缺陷叠加时，修好一个会让另一个以新症状浮出来**，别把新症状当回归。

### ★★ 第二条教训：**"镜像常量"式的判据抓不住"常量本身是错的"**

那条噪声用例拿 `pixel_at()` 读回 **u8** 再 `as f32` 得到 **0..255** 的基准，
而着色器内部是 **0..1**；两边只有 `NOISE_FULL_SCALE` 一个换算系数
⇒ **同一个错误值同时写进着色器和测试镜像，模型自洽、判据恒绿**。
它验的是"实现与它自己的镜像一致"，不是"实现与真实渲染一致"。

**修法**：删掉那三个"逐行移植"助手（它们就是那面自洽的镜子），
判据改为只验三条**物理性质**（幅度在契约量纲内 / 三通道相同 / 分布散开），
并新增 `pixel_at_norm()`。①' 判据从 `max_abs > 100`（**旧阈值把错版本当基准 ⇒ 在保护 bug**）
改成双向：`> 0.2*want` 且 `<= want*1.5`。

                        ⇒ 平滑过渡，画面**始终在**

### 根因（我定位到行号）
1. **幅度实测 ±112.8**（由相邻像素差 std 反推），而 `(n-0.5)×255×0.08` 应只有 **±10.2**；
   `weight ≈ 1.0` 的预测是 **±127.5** ⇒ **`amount: 0.08` 实际上没有生效。**
2. 转译产物里 `noise` 效果的形状是：
   ```json
   {"kind":"noise","params":{"amount":0.08,"seed":7}}
   layer.opacity = 1, layer.blend = "normal"
   layer.keyframes = [{frame:0,value:0},{frame:3,value:0.972},...]   ← 包络在**图层**上
   ```
   ⇒ **`effect.opacity` 字段缺失** ⇒ 底座 `timeline.rs:530` 的
   `let strength = effect.opacity.clamp(0,1)` 取**默认 1.0**。
3. 底座着色器 `color_mask.wgsl:137`：
   ```wgsl
   rgb = rgb + vec3((n - 0.5) * NOISE_FULL_SCALE * mask.noise_amount);   // NOISE_FULL_SCALE=255
   ```
   `rgb` 来自 `Rgba8Unorm` ⇒ **0..255**，而 `noise_amount` 契约 0..1 ⇒ 乘法量纲是对的。
4. ★★ **底座自己知道这个洞**：`timeline.rs:2548-2554` 的测试注释写着 ——
   > 在真实 GPU 上**反解出增量比 `amount` 该给的大了一个数量级**
   > （`amount=0.08` 观测到 **`+171`** 的跳变，而按 `(n-0.5)*255*amount` 最多只有 ±10）。
   > 本用例把"参数有没有被谁乘过"在纯函数层钉死 —— 如果这里是对的，
   > **那多出来的放大只能来自渲染路径**，排查范围立刻缩到一处。

   ⇒ **底座当时把这个洞"钉住参数层、留给渲染路径"，但没再往下查。**
   **我这次测到的 ±112.8 就是这个悬案的实体。**

### 精确机制（我逐行查到）
底座有**两条互不相通的不透明度通道**，转译器只喂了其中一条：

| 通道 | 载体 | 谁读它 | 转译器喂了吗 |
|---|---|---|---|
| **① 图层合成不透明度** | `layer.keyframes` → `opacity_scale` |
`timeline.rs:1753` `opacity: layer.opacity * opacity_scale` | ✅ **喂了**（包络 0→0.972） |
| **② 效果强度** `strength` | `effect.opacity` |
`timeline.rs:530` `let strength = effect.opacity.clamp(0,1)` | ❌ **没喂** ⇒ 取**默认 1.0** |

而 `noise` 的幅度是 `amount × strength`：
```
amount  = 0.08      （转译器给的，正确）
strength= 1.0       （effect.opacity 默认值 —— 包络**没有**进来）
⇒ noise_amount = 0.08  …… 但实测幅度是 ±112.8，而 0.08 应给 ±10.2
```

⚠️ **还有一处没解释**：即使 `noise_amount = 0.08`，也不该出现 ±113。
⇒ **底座那条 `+171` 悬案（"多出来的放大只能来自渲染路径"）就是这里**，
**我没有继续下钻到 GPU 侧**（跨仓、且需授权）。**这一条如实标为未定。**
★ 但**已足以下结论**：`amount` 与包络**没有以预期的方式合到一起**，
而且**同类 `amount × strength` 的乘法在底座里有 8 处**（`grep -c`），
`overlay` 却是好的 ⇒ **很可能是一整类，但只确认了 `noise` 中招。**

### ★★ W1 根因（**已定量，不再是"待确认"**）

**反推**：实测噪声幅度 **±112.8** ⇒ `amount_有效 = 112.8 / (0.5 × 255) ≈ **0.885**`，
而转译器给的是 **0.08** ⇒ **`params.amount = 0.08` 被丢弃了，`noise_amount` 实际接近 1.0。**

**为什么 `flash` 不坏、`noise` 坏 —— 两者合成方式根本不同**（着色器原文）：
```wgsl
// flash（:109）—— 有界插值，amount 再大也不会越界
rgb = mix(rgb, flash_color, mask.flash_amount);

// noise（:137）—— 无界加法，amount 大就冲出 [0,255]
rgb = rgb + vec3<f32>((n - 0.5) * NOISE_FULL_SCALE * mask.noise_amount);   // NOISE_FULL_SCALE = 255
```
⇒ `flash` 用 `mix`，**数学上有界**；`noise` 用 `+`，**无界**。

**阈值表**：
| amount | 摆动 | 占满量程 |
|---|---|---|
| 0.08（**本应如此**） | ±10.2 | ±4.0% ← 正常 |
| 0.4 | ±51.0 | ±20.0% |
| **0.885（实测反推）** | **±112.8** | **±44.2%** ← 画面被冲掉 |
| 1.0 | ±127.5 | ±50.0% |

⇒ **`noise` 的"漏乘 amount"之所以后果特别严重，是因为它是唯一的无界加法合成。**
**同样的 bug 落在 `flash` 上只会"闪得比预期白一点"，落在 `noise` 上就是"画面没了"。**

### §9 多版本成片 —— **已修**（两个独立缺陷：一个静默假成功 + 一个无界面）

#### 缺陷 A：**静默假成功**（我本轮实测撞到）
`--versions 3` 跑完：日志三行「版本 N/3：开头选在 X」、收工还宣称「已恢复到第一版的开头」，
而 **三个产物 MD5 完全相同**（`a6f7f120…`），第 1 帧与第 10s 帧**逐像素相同**。**报告与事实相反。**

**根因**（两条独立守卫，各自都足以致命）：
```
duration_for_versions 读 data/clip-meta.json，缺失 ⇒ 回落 0.0
→ edl_clips_from_mute_complement(ranges, 0.0) 对非正时长返回空 Vec
→ set_opening 在 base.is_empty() 处 return，一个字节都不写
→ 每一版渲染的输入完全相同
```
**修法**（两层，都在调用方）：① 出片前**时长预检**（读不到就 bail 并指路 `polish process`）；
② 逐版**写后回读自检**（确认 `source_start` 真的等于候选值，否则 bail）。

#### 缺陷 B：**无界面**
`--versions` **只有 CLI 有**；`/api/polish/render` 里 `versions` **零命中** ⇒
WebUI 点「渲染导出」永远只出一版，用户**在界面上根本够不到**这个能力。
**修法**：后端 `PolishJobOpts.versions` + handler 读 `body.versions`（非整数/超 10 **400**）
+ `runRender` 透传 + 弹窗「版本数」下拉。

#### 真机证据
| 项 | 证据 |
|---|---|
| 修前（复现） | 缺 `clip-meta.json` ⇒ 3 版 MD5 **全等** `a6f7f120` |

| 修后（正常） | 有时长 ⇒ 3 版 MD5 **各不相同**，时长 **39.80 / 37.60 / 35.40 s**，逐版短 **2.2s**，与开头位移 `0.20→2.40→4.60` **精确对应** |

**两个缺口，第二个比第一个更严重**：

① **改不了也看不见**：选中 `element` 事件时，属性面板只显示一行**只读**的
「类型 元素（文字 / 贴纸）」—— 没有文字内容、样式、纵向位置。
② **新建出来的元素是死的**：`defaultEvent('element', t)` 只产出 `{type, time, end}`，
**没有 `kind`** ⇒ 出片侧走 `元素 kind = "" 认不出` ⇒ **DROP**。
⇒ 用户「新建一个元素」的真实结果是：**界面上什么都没有、成片里也什么都没有**。

**修法**：
- 属性面板加 `element` 分支：元素种类（text / sticker）+ 文字内容 + 样式四档 + 纵向位置三档。
  ⚠️ **没有折进 `type === 'sticker'` 分支** —— 那是老的 `sticker` 变体，字段名完全不同
  （`keyword` vs `kind` + `text`）。
  ⚠️ 样式四档与出片侧 `TEXT_STYLE_FALLBACK` **同集合**（`hook`/`chapter`/`comment`/`count`）；
  **数值（字号/描边/颜色）不在前端抄一份** —— 那是出片侧的活，抄了就会漂。
  ⚠️ 如实写明「横向位置由后处理按安全落点算」，**不做成能拖的假控件**。
- `defaultEvent` 补 `element` 分支：`kind='text'` + `text=''` + `style='comment'` + `pos='bottom'`。
- `setElementKind`：切 `kind` 时同步换载荷字段；**反方向不清 `text`**（用户可能只是点错了）。

**真机证据**（真服务器 26496 + 真 Chrome CDP，工程里插一条 `E4A-UI-MARKER`）：
| 项 | 实测值 |
|---|---|
| 贴纸轨上的块 | 紫色 `element` 块，几何 **360×20 @ x559** |
| 元素种类 | `text` → 「文字（大字标题 / 章节 / 注释）」 |
| **文字内容** | **`E4A-UI-MARKER`**（= 工程里的真值，不是空壳） |
| 样式 | `hook` → 「钩子（最大字）」 |
| 纵向位置 | `center` → 「中」 |
| 开始 / 结束 | `2` / `8` |
| 几何断言 | label **195×19** · select **195×35** · input **195×33** —— **全部 > 0** |

★ `defaultEvent` 的修复用**直接执行**验证（把函数抽出来真跑）：
`element => {type,time,end,kind:'text',text:'',style:'comment',pos:'bottom'}`
**反证**：缺 `kind` 的 element 在转译器里走 `元素 kind = "" 认不出` ⇒ **DROP**。

★ **一次自己撞的坑（值得记）**：我第一次把探针事件插错了位置（插在段头字段之前），

### §5 E3 预览侧文字元素 —— **已接通**（消掉"成片有字、预览没有"的真分叉）

**分叉的成因**：出片侧能画文字元素（A/B 帧已验），而预览侧 `getElements` 对
`kind !== 'text'` 直接 `continue` ⇒ **成片有字、预览没有，而且不报错**。
它原来的免责理由是「转译器会在报告里明说这条」—— 而转译器那条 `drop()` 早就换成了真实现，
**兜底不存在了**。

**★ 关键判断：这里不去"近似"任何东西。**
`process` 的 Step 1d3 `layout_text_elements` 早就把**落点**（`x`/`y` 百分比）与
**解析后的样式串**写回事件了 —— 预览只是**读**，不是自己推一份。
所以原来那句"故意不近似（怕大字压住主播脸）"的顾虑**在这里根本不适用**：
读一份已经算好的值 ≠ 自己近似一份。这也正是本仓对付"两份实现漂移"的既定形态。

**改动**：`buildIndex` 的 element 分支加 `kind === 'text'` 支；新增 `parseTextSource` / `numPct`；
`getElements` 加 text 支（**复用贴纸同一条进出场曲线**）；`PolishPreview.vue` 加 `.text-layer` / `.text-el`。
⚠️ **样式串读不出时"不画"** —— 不自己编兜底数值去掩盖"内部不一致"。

**真机证据**：
| 层级 | 实测 |
|---|---|
| **单元级** | 直接 `import engine.js` 真跑：`t=5` ⇒ `{isText:true, text:'PREVIEW-TEXT-OK', style:{fontPx:120, weight:900, strokePx:8}, xPct:6, yPct:16, opacity:1}`；`t=25`（窗口外）⇒ **0 条** |
| **页面级** | 真服务器 + 真 Chrome，标尺 seek 进窗口后 `.text-el` **真的出现**：`opacity=1` · `font-size=120px` · `color=rgb(255,255,255)` · `stroke=8px`，**与 `source` 串逐项对得上** |
| **视觉** | 截图 `docs/plan/preview-text-element-2026-10.png`：预览画面里**肉眼可见那行白字**（叠在彩条测试图上） |

★ **探针过程的一个坑，值得记**：我前几次点击**全部落空**，因为**设备尺寸覆盖被页面重载重置**
成 764×429，而标尺在 `y=1635` —— 点击事件打在了**视口外面**，
**而且没有任何报错**（不是异常、不是 404，就是"没反应"）。

⇒ 教训：**"点了没反应"要先怀疑坐标在不在视口内**，别先怀疑代码。

## §5 E4a **T3 强调** —— 决定记录：**明确不做**（不新增触发源）

计划这项写的是「**决定**：要么新触发源，要么明确不做」。**做的是"明确不做"**，理由如下
（正文在 `crates/yekitrim-polish/src/render/elements.rs:32-48`，那是权威）。

### 通道是好的，缺的是**触发源**

* **底座通道已就绪**：`Cue.scale: Option<f32>`（`None` = 1.0），乘法合成
  `line.scale × enter_scale × cue.scale`，判据齐、变异自证过（Dhampir `ac97b70`）。
* **但它是"逐条"的**，而本仓这条路**从头到尾不存在"哪几个字是关键词"这个信息**。
  底座那个字段的文档写着"哪几条命中是**宿主**知道的（按 `<span class="hl">` 标记判）"——
  实测本仓这条**从来不产这个标记**：
  ```
  tools/polish-to-dhampir.mjs:3371  const textBody = String(event.text ?? '');  ← 原样透传
  process/mod.rs 里 'class="hl"'                                     → 0 命中
  .hl 的生产者只有 cover.rs（封面）/ takumi.rs（封面测试）           → 都不在这条路
  ```

### ⚠️ 为什么**不许**拿 `filter.highlight_keywords` 顶替

那是**封面**的字段（`cover.rs` 消费）。借来的后果是
「**用户改了封面高亮设置，成片里的文字动效跟着变**」——
一个字段两处语义，而且**症状是静默的**（没人会往"我刚改的是封面"那想）。

**这属于本仓最贵的那类错：跑得通、不报错、结果不对。**

### 真要做 = **新功能，不是接线**

要同时定「关键词从哪来」+ 改 `process`（把标记写进 `event.text` 或新字段）+ 提示词
+ 前端 —— **单开一批**，不属于"把已有能力接上"。

⇒ 所以 `ElementsConfig` 里**没有** `emphasize_*` 字段，转译器也**不写** `cue.scale`。
底座那份 `Cue.scale` 通道**空转着，等产品决策**（不是坏了，是没得接）。

⚠️ **本决定是可逆的**：一旦有了真正的关键词来源（例如 LLM 在 `kind=text` 的事件上
产出关键词字段），接线本身是**小改动**（`process` 写标记 + 转译器读标记写 `cue.scale`）。
现在不做，是因为**没有触发源就不要造一个假的**。
