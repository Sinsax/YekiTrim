## 一、层面 2 的 5 条路（关键岔路）

底座现状：**文字 → 生成 SRT → 起 ffmpeg（`subtitles=` → libass）→ 拿回一整行位图**。
和参照实现（HTML 逐字 DOM + canvas 量字）是两个不同的模型，所以逐字效果缺位。

| 方案 | 做法 | 能拿到 | 成本 | 风险 |
|---|---|---|---|---|
| **A · 全换自绘** | 丢掉 libass，自己排版 + 画字 | 全能力 | **极大** | **所有文字像素再变**；要吃下字体回退 |
| **B · 留 libass + ASS 标签** | ASS 里写 `\t() \pos() \frz` | 部分逐字 | 中 | ⚠️ **已查证：与现有实现硬冲突，见下** |
| **C · 拆两条路** | 字幕走 libass / 文字元素走自绘 | 文字元素全能力 | 中-大 | 要区分轨类型；只改文字元素则老工程不变 |
| **D · 只读已有字段** | 让文字读 `TransformV2.rotation` | **倾斜 + 摇摆共 6 档** | **极小** | 无 |
| **E · 扩 `TextItem`** | 逐段 → 逐字，字仍由 libass 画 | 逐字字号/旋转/位移 | 中 | 每帧一次 ffmpeg |

### ⚠️ 方案 B 已查证不可行（重要）

底座**特意**选了 `subtitles=`（SRT）而不是 `ass=`，理由写在 `text_raster.rs` 里：

> `ass=` 的 `Dialogue:` 文本里 `%{n}` 是 **ASS 覆盖标签**，会被 libass 当指令**吞掉**
> （实测：`%{n}` 只剩 312 个覆盖像素、而「笑靥如花」是 2180 个）。
> 那是"用户打的东西被悄悄吃掉"……
> `subtitles=` 让 libass 自己解析 SRT，`%{n}` 原样画出来。

⇒ **要用 ASS 标签（B），就得换回 `ass=`，等于把"用户文本被静默吞掉"这个坑重新挖开。**
除非同时对用户文本里的 `{` `}` 做转义 —— 但那又要重新验证"转义后 `%{n}` 仍然原样"。
**B 的账面成本是"中"，实际是"中 + 一个已修复 bug 的回归风险"。降级。**

### 方案 D 的技术细节（最推荐的第一步）

**已查证**：
- `Layer.transform: TransformV2 { x, y, scale, rotation }` **字段已存在**（`layer.rs:386`）
- `text_overlay.rs` **完全不读 `transform`**（grep 零命中）
- 绘制路径是 `evaluate_overlay(...)` → `painter.paint(&mut image, ...)`，
  对着一张 **RGBA 位图** 操作 ⇒ 在这一层做仿射变换**位置是够得着的**
- `text_overlay::blit` 已经做"位图按行拷进内存图"，加旋转是同一个函数的延伸

⇒ **改动：让文字路径读一次 `rotation`，在 `paint` 里对位图做旋转。**
不碰栅格化器、不碰 SRT、不碰缓存键。

### 方案 E 的技术细节

**已查证**：`TextItem` 已经是**逐条**携带变换的形态，且有先例：

```rust
pub struct TextItem {
    pub text: String,
    pub rect: NormalizedRect,
    pub opacity: f32,
    pub dy_px: f32,   // 契约层算好的纵向偏移
    pub dx_px: f32,   // T4 加的横向通道（"抖动是两维的"）
    pub color: [u8;4],
    pub font_px: ...,  // 字号（布局算出来的事实，跟着条目走）
    ...
}
```

⚠️ 注意 `dx_px` 的注释已经建立了**先例**：

> 在 T4 之前，文字的位移只有"入场上浮/退场上移"这一种，而它**只有纵向** ——
> 于是这个字段不存在……抖动是**两维**的（只抖一个方向看着像"在呼吸"而不是"在抖"），
> 所以横向必须单独有一条通道。

⇒ **"逐字变换"可以照同一个形状加**：加 `per_char: Option<Vec<CharXform>>`，
`None` = 老行为（逐字节不变）。这与 R4「零回归」口径一致。

## 二、三条路的关系（不是互斥的）

```
D（读 rotation）  ──┐
                    ├── 都是"不换栅格化器"的渐进改良
E（扩 TextItem）  ──┘
                    └── 到 E 的尽头会撞上"每帧一次 ffmpeg"

A（全自绘）──── C（拆两条路）的"文字元素"那一半就是 A 的缩小版
```

**D → E → C** 是一条渐进路线；**A** 是 C 的激进替代（连字幕也换掉）。
**B 建议放弃**（见上）。

## 三、成本上最关键的一个未解问题

**逐字动画 = 每帧文字都不同。** 而底座的位图缓存键含"文本 + 字号 + 描边 + 字体 + 尺寸"：

> 一条字幕在 30fps 下要在几十帧上出现……不缓存就是每条字幕几十次 ffmpeg 进程。

⇒ 如果逐字动画真的走"每帧渲染"，就是**每帧一次 ffmpeg 进程**。

**这个问题必须先有答案，才能选 D/E/C：**
- 若摊得掉（例如一次进程渲多个字/多帧）→ **E 可行**
- 若摊不掉 → **E 只能用于静态逐字效果**（逐字字号/旋转/位移但不动），
  而"逐字别峰动画"（跳起/逐字弹出）**只能预览、成片降级**
- 若必须支持逐字动画 → **绕不开自绘（C）**
