## 1. 决策理由（Rationale）★★★

**预期效果**
用户看到的不只是"切好的片子"，还有**每个决策的理由**：
"开头选在 04:12，因为这里是爆点前 3 秒且落在句末"。
从"黑箱工具"变成"**可以问为什么的合作者**"。

**详细内容**
- 每个自动决策点带一个 `reason` 字段（枚举 + 人话文本）；
- 覆盖：边界、删减、头尾选择、爆点判定、特效配额；
- 落盘进 `polish.toml`，**可在日志/界面显示**；
- ⚠️ **不需要任何新架构** —— 今天**零个** `reason` 字段（已 grep 核实）。

**依据**：LAVE（Meta + UofT + UCSD, [ACM IUI 2024](https://www.dgp.toronto.edu/~bryanw/lave)）——
*"explains its rationale for the trimmings... For transparency"*。

**为什么排第一**：**成本极低、且是后面所有"自动决策"的信任基础**。
没有理由的自动剪辑，用户永远不敢放手让它跑。

**详见**：`conversational-editing-and-music.md` §1.1 / §4 (N1)

## 2. 句末边界守卫 ★★★

**预期效果**
不再"**一句话说到一半就切**"。观众感觉从"剪得莫名其妙"变成"切得干净"。

**详细内容**
- **硬约束**：切片/分段边界必须落在**句末**（字幕文本以 `。！？…` 结尾，或与下一条间隔 > 0.35s）；
- **硬约束**：爆点窗口内不许设边界；
- 落到 `polish.toml` 的可审计结构（见 §9 的 `[editing.boundaries]`）；
- ⚠️ **不需要词级时间戳** —— 字幕自带 `text` + `start/end`，"这条是不是以句末标点结尾"就够。

**依据**：HIVE 论文（[arXiv 2507.02790](https://arxiv.org/html/2507.02790v1)，中科大 + 字节）——
*"ensure that clip boundaries do not interrupt ongoing dialogue"*。
**量化**：去掉边界选择，**Hook Rate 从 0.87 掉到 0.28**（掉 2/3）。

**现状核实**：本仓分段提示词只有一句**软要求**"优先在字幕间隙 >2s 处切段"，
**没有任何守卫**（`snap_start`/`snap_end` 只保护特效时间，不保护段边界）。

**详见**：`editing-decision-layer.md` §5.2

## 3. 剪辑质量分（Smoothness）★★★

**预期效果**
每条切片有一个**可比较的数字**（"这条 4.5 分，那条 2.1 分"）。
今天本仓**完全没有**"剪得好不好"的量化 —— 只能靠人看。

**详细内容**
```
Smoothness = 时长 / (1 + 干扰次数)
```
四个**本仓可自动算**的干扰项：
| 干扰项 | 判据 |
|---|---|
| 边界落在句子中间 | 字幕文本 |
| 切在爆点上 | 弹幕/情绪 |
| 静默突变（突然没声） | 音轨 |
| 两次视觉变化间隔 < 0.8s | 事件表 |

用途：**切片列表显示** + **对比不同参数**（调参终于有了客观依据）。

**依据**：HIVE 论文的 Smoothness 定义。**注意只抄它的"构造"，不抄它的广告评测口径**
（Hook Rate / Suspense Rate 要人评，本仓场景不同）。

**详见**：`editing-decision-layer.md` §7.1

## 5. ⭐ `elements` 元素系统（文字 + 贴纸）★★★

**预期效果**
**画面上第一次能放"文字"** —— 钩子标题、章节卡、吐槽、计数（"第 3 次"）。
今天本仓**完全没有**这个能力，所有"想写一句话"的需求只能退化成贴纸图（不达意）。

**详细内容**
```toml
[[elements]]
kind = "text"        # 或 "sticker"（现有）
text = "这就是传说中的…"
style = "hook"       # hook | chapter | comment | count
pos = "top"
```
| 层 | 名字 | 说明 |
|---|---|---|
| 顶层零件 | **`elements`（元素）** | "叠在画面上的东西" |
| 子类型 | `sticker` | 图/GIF（现有能力） |
| 子类型 | `text` | **纯文本（新增）** |

- ⚠️ **不可叫 `overlay`** —— 那个 id 已被"氛围色罩"效果占用，两个同名会让门禁和人都分不清；
- 底座表达：**不需要底座改**（文字本来就有 `AssetKind::Subtitle` / `TextOverlay` 链）；
- 白拿的复用：折行/安全宽（`wrapCaptionParts`）、与字幕带错开（`caption_band`）、封面排版观感；
- ⚠️ **主要工作量**：`placement.rs` 现在按 `280×SK` 固定盒算障碍，文字是**变宽高** ⇒ 落点求解器要支持动态盒；
- 轨道：**沿用 lane key `sticker` 不改，只把显示标签改成「元素」**（老工程零迁移）。

**为什么是"元素"而不是"新事件类型"**：共享落点求解器、共享素材链、用户视角是一类东西。

**详见**：`polish-enrichment-proposal.md` §2.2

## 6. 爆点判据多信号 ★★

**预期效果**
无弹幕文件时**也能定位爆点**（不再静默失效）；有弹幕时**不再系统性地晚约 3 秒**。

**详细内容**
修正后的判据链：
| 信号 | 可得性 | 角色 |
|---|---|---|
| **字幕**（情绪词、句密度） | **必然有** | **主判据** |
| 音效/响度 | 有音频就有 | 次判据 |
| 弹幕密度 | **不一定有** | 有则加权，无则跳过 |

- 滞后校正是**微调**（`offset_secs` 默认 −3.0，本仓口径），**无弹幕整条跳过**；
- ⚠️ **无弹幕时必须日志明说**"本次无弹幕信号，爆点按字幕判"——**不许静默降级**；
- 弹幕 `analyze` 加多特征（平均消息长度 + 相似度）区分"刷屏"vs"真高潮"——**可选增强**。

**⚠️ 一个必须知道的旧错误**：曾有版本把"弹幕滞后 20s"当 P0 硬依赖 ——
那是外部论文在特定游戏品类的值，**本仓口径是 −3s**。已按本仓口径修正。

**详见**：`polish-enrichment-proposal.md` §2.6

## 7. 静默分两类 ★★

**预期效果**
**保住笑点后的停顿**。从"工具不懂喜剧"变成"懂节奏"。

**详细内容**
| 沉默类型 | 判据 | 处理 |
|---|---|---|
| 拖沓沉默 | 前后无爆点信号 | 照旧剪（可压到 ≤1s） |
| **喜剧停顿** | 紧跟爆点（`punch` 段/弹幕峰值/响度峰值）之后 | **保护**（不剪，或只留 0.25s 呼吸口） |

**依据**：两个独立来源（[chokiru](https://chokiru.com/blog/-YgwBCF) 音效指南、
切り抜き師 [Zuppin'](https://note.com/zuppin/n/n9ed56f2b3f39)）+ 开源实现 HotClip，
都指出"**爆点后的短沉默是笑点发酵期**"。

**现状风险**：本仓 `DEFAULT_MIN_GAP_SECS = 3.5s`，**间隔 > 3.5s 就剪** ⇒
一个 4 秒的包袱停顿被剪成 2.4 秒，**正好砍掉喜剧节拍**，而且是**自动**发生的。

**详见**：`polish-enrichment-proposal.md` §3.4

## 8. `role` 叙事角色（三档先行）★★

**预期效果**
整片**有起伏**：钩子 → 铺垫 → 蓄力 → 爆点 → 余韵。
今天的问题：**每段都挺热闹，整片没有形状**（LLM 逐段局部决策，必然平均用力）。

**详细内容**
```toml
[[segments]]
role = "hook"    # 新增：hook | setup | build | punch | afterglow | cta
fx = "high"      # 保留（老工程缺 role ⇒ 语义回到 fx）
```
| `role` | 配方（自动做什么） |
|---|---|
| `hook` | 大字 + 强音效 + 硬切；≤5s、至多一段 |
| `setup` | **几乎不放特效**（守住"静"，才有"动"的对比） |
| `build` | 缓慢推近、密度上升 |
| `punch` | 近景/画中画 + shake + flash + 音效**全上** |
| `afterglow` | 拉远、**留白**、静默 |
| `cta` | 大字 + fade_out |

- **守卫**（照 `cap_pip_shots` 先例）：`hook` 至多一段；全片至少一个 `punch`；`setup` 不超 40%；
- **配额跟 role 走**：`punch` ×2、`setup` ×0；
- ✅ **不加 API 往返**：Step 1 本来就是全局单次调用，`role` 只是同一 JSON 里多一个字段；
- **建议先做三档**（`hook`/`punch`/其余）——拿到 80% 起伏感，改动面小得多。

**详见**：`polish-enrichment-proposal.md` §3

## 9. 多版本成片 ☆

**预期效果**
**同一份素材出 3 条片子**，开头/结尾不同，用户挑一条。
这是今天完全不具备的形态（一条道走到黑）。

**详细内容**
- 为同一素材产出 N 组 `(opening, ending, prune)` 组合；
- **共用同一份效果事件**（演出层不变）⇒ 成本低；
- 论文硬约束：**开头/结尾不取爆点内部**（保叙事完整）；
- 本仓 `unique_output_path` 已支持"同名加 `_1`/`_2`"，**不需要改产物机制**。

**依据**：HIVE Algorithm 1（枚举 opening × ending 组合）。

**详见**：`editing-decision-layer.md` §5.3

## 10. 情绪轨道 ☆

**预期效果**
画面按"**观众是在笑还是在惊**"来演 —— 而今天只知道"这里很热"。
**震惊和爆笑该配的画面完全不同**（震惊→静音+闪白；爆笑→抖动+贴纸）。

**详细内容 —— 本仓有一个被完全浪费的信号源**

| 信号 | XML 里有 | 今天用了吗 |
|---|---|---|
| 条数 | ✅ | ✅ **只用了这个** |
| **文本** | ✅ | ❌ 读进来了，但 `analyze` 只 `counts[idx] += 1` |
| **颜色** | ✅ 已解析成 `#rrggbb` | ❌ **零生产消费者**（已 grep：只有测试断言） |
| **模式** | ✅ | ❌ 只用来定一个 y 坐标 |

- **颜色尤其可惜**：B站**彩色弹幕是花钱的**（普通白色，彩色要舰长/付费）⇒
  **一条弹幕的颜色 = 观众愿意为这条情绪付费**（比条数硬得多）；
- **文本最富**：弹幕文本 + 时间戳 ≈ **一份免费的人工情绪标注数据集**；
- 三层融合：词表（零成本）→ 颜色/模式加权（零成本）→ LLM 打标（可选）；
- ⚠️ **无弹幕必须能跑**（退到字幕情绪 + 日志明说）。

**详见**：`emotion-narrative-engine.md`

## 11. BGM + 卡点 ☆

> ⚠️ **本项已按用户口径修订**：**本仓没有 BGM，音轨全是直播原声** ⇒
> **"卡点"是前提缺失、不是待做项**（没有节拍网格可对）。
> **所以这一项的正确表述是"先引入 BGM"** —— 卡点只是它**可能的后续**。
> ⚠️ 调研那套"音乐让路给人声"的 `sidechaincompress` 参数**也不适用**（见 §0b.2）。

**预期效果**
**爆点切在音乐强拍上** —— 这是短视频"爽感"的本质。今天本仓**完全没有这个轴**。

**详细内容**
```
① 选 BGM（用户自带/素材库）
② 分析音乐结构 → 节拍 / 段落 / 强拍位置
③ 排演出 → 爆点对齐强拍、铺垫放低能量段
④ 出片 → 画面切点由音乐决定 + BGM 混入（带 ducking）
```
- **因果关系倒过来**：不是"剪好再配乐"，而是**音乐结构决定画面切在哪**；
- ⚠️ **已核实本仓零基础**：全仓每一处 "BGM" 都是"**把 BGM 从 ASR 里排除掉**"，从没当剪辑元素；
- ✅ **地基齐全**：响度分析（`ebur128`）+ 混音（`mix_sfx`）都在，
  且**音轨归本仓（`--no-audio`）⇒ 不需要底座改**；
- ⚠️ **版权**：只支持用户自带 / 素材库，**不自带任何音乐文件**。

**依据**：CutClaw（[HF 2603.29664](https://huggingface.co/papers/2603.29664)）——
*"anchoring visual scenes to musical shifts"*。

**一个交叉**：`§7` 的"静音"在音乐骨架下多一层含义 —— **把音乐也抽掉**
（"drop 前的一拍空白"，电子乐最经典的张力手法，**可自动生成**）。

**详见**：`conversational-editing-and-music.md` §2

## 16. 建议的推进顺序（分四批）

## ⚠️ 本版本最有价值的三条教训（都是"全绿但其实是坏的"）

| # | 缺陷 | 为什么全门禁抓不住 |
|---|---|---|
| 1 | **`polish_project_put_locked` 漏了 4 个键** | 它是**逐字段白名单**：没列的键 **PUT 照回 `{"ok":true}`、磁盘一字不动**。症状是"toast 说已保存、控件回弹、无报错" —— build 绿、门禁全绿、**能通过验收**。⇒ **新增配置字段先 grep 字段名，命中 0 次就要补分支。** |
| 2 | **`parseStroke` 的 `{6}` 让 `#fff` 静默变深灰** | `hexColor` 一直能展开 3/4 位，错的是**调用点上那道前置 `match`** ⇒ 用户选白描边、成片是深灰、**报告里一行差异都没有**。（已修根 + 加守卫：`checkStroke` 9 项 + 第 43 条变异）。⚠️ **只测 `hexColor` 抓不到它。** |
| 3 | **多行字幕落点算错（第一版）** | `cy` 是**文字块中心**，块内 N 行绕它铺开 ⇒ 正确式 `cyEff = CH - (pct/100)*CH - N*lh/2`。第一版写成 `+行盒/2`（**只对 N=1 成立**）：2 行偏 108px、3 行偏 216px 且**不报错**。 |
| 4 | **假绿**（自己写的测试） | 断言"键被删掉"时**复用了写盘之前读的 `raw`** ⇒ 断言永远成立。`raw` 是合法变量、类型也对，**读代码看不出来**。⇒ **读盘必须在写盘之后 + 变异自证。** 配方见 `docs/polish-right-column.md` 末节。 |
