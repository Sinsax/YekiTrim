# 预处理步进区改造 + 阶段可选 + 剪出子阶段进度 —— 整合计划（2026-11-15）

> 用户口径：①步进区（识别/找亮点/剪出片段）塞入**复选框**，有时不需要全剪辑 —— 默认只勾
> **前三阶段**（提取音频/识别/查找事件），剪出片段不勾（剪辑太费时间和性能）；②「找亮点」
> 改名「**查找事件**」；③步进区塞入**复选的进度 + 整体进度 + 一键处理按钮**；④接上此前
> 收集的可补充项 1+2+3（剪出收尾子阶段进度 / 100% 语义 / 剪切明细）。
> 实测依据：2026-11-15 真实运行 —— Cutter 24 分钟（批次进度正常），[Cutter] completed 后
> `init_polish_for_events` 收尾循环 40+ 片段 × 10-55s = **14+ 分钟零事件**（「100% 卡住」假警报）。

## A. 阶段可选（复选框，累计语义）

- **UI**：步进区三个节点各带一枚复选框（识别声音 / 查找事件 / 剪出片段）。
  **累计模型**：勾后面的自动勾上前面（剪出片段 ⇒ 查找事件+识别声音）；取消前面的同时取消后面。
  默认 = **识别声音 ✓ + 查找事件 ✓ + 剪出片段 ✗**（= 管线前三阶段，剪出不跑）。
  选择持久化 `localStorage["yekitrim.prepare.stages"]`（认不出的值回落默认）。
- **映射**（节点 → stages 参数）：识别声音 → `["extract","transcribe"]`；查找事件 → `+"detect"`；
  剪出片段 → `+"cut"`。勾了识别才允许勾查找事件（前置未勾时后置复选框禁用 + title 说明）。
- **⚠️ 服务端分派修正（本项的前置硬依赖，现况是错的）**：
  `yekitrim_service::run_stages_with_ext` 目前「多阶段列表 → 一律 run_process 全流程」——
  复选框发来 `["extract","transcribe"]` 会**把剪出也跑了**，恰好违背本功能。
  改法：多阶段 = **按序逐个 `run_stage`**（它已处理各阶段前置与自动补提取、落盘路径）；
  `"process"` 单键仍走 run_all 全流程（语义不变）。改完 `expected_stages` 同步改为
  "按请求列表逐个映射"（i/N 按**实际会跑**的阶段数，不再假设多阶段=全流程）。
- **按钮语义**：一键处理 = 按**当前勾选**的阶段列表起 `stage_process` 任务（kind 不变）；
  勾选含剪出时行为与旧全流程一致。已有产物时的重跑语义沿用单阶段命令的口径（可重跑）。

## C. 步进区改造（范本）

```
┌────────────────────────────────────────────────────────────────────────────┐
│ [☑] 识别声音   ── [☑] 查找事件   ── [☐] 剪出片段        [一键处理 ▶] [去挑片段] │
│  ✓已完成         ✓已完成           （未勾选）                                │
│ 整体：阶段 2/2 已完成 · 上次运行 4h11m（或运行中：阶段 1/2 · 识别声音 · 37%）    │
└────────────────────────────────────────────────────────────────────────────┘
```

- **节点** = 复选框 + 名称 + 状态（已完成/已剪出/未勾选 —— 现有状态保留）。
- **整体进度行**：空闲 → 「阶段 i/N 已完成」摘要；运行中 → 复用 `jobLine` 的进行时行
  （阶段 i/N · 中文名 · 明细 · %，N = 本次勾选的阶段数）。几何断言照纪律做。
- **一键处理按钮**落进步进区右侧（与「去挑片段」并存：一个发起、一个导航）。

## D. 剪出片段子阶段进度（接上轮收集 1+2+3）

1. **收尾子阶段进度**：`init_polish_for_events`（service/core_pipeline.rs:151，调用点 :316 / :488）
   加 reporter 参数 → 循环内 `stage_progress(i, N)` + `note("补精修工程 12/40：片段标题…")`。
   阶段语义：`[Cutter] completed` 后任务仍在跑（run_process 的 Stage 4 收尾），进度条**重新爬升**
   （剪切 0-100 → 收尾 0-100），message 明示「剪切完成，补精修工程中」。
2. **剪切进行中明细**：`cutting/mod.rs` 逐批次完成时 `note("正在剪出 clip-12：标题…")`
   （与现有批次百分比互补；按完成序报，批内 3 并发）。
3. **收尾计入阶段 4 的整体观感**：expected 阶段数不变（收尾不算独立阶段），i/N 停在 4/4，
   由 message + 重爬的进度条表达收尾 —— 不把两种进度混进一根条。

## E. 验收判据

1. 勾选默认（前两节点）点一键处理 → 任务**不含剪出**：日志无 `[Cutter] started`，产物无新片段；
   任务行显示「阶段 1/2 · 提取音频 → 2/2 · 查找事件」并按阶段推进。
2. 勾全三项 → 与旧全流程行为一致（回归）。
3. 剪出运行中：剪切期 note 逐片段可见；收尾期进度条重爬 + 「补精修工程 i/N」；
   全程无 >120s 无事件窗口（stuckNote 只在真卡住时响）。
4. 全 UI 无「找亮点」字样残留（grep 判据），英文类名零漏出（既有 STAGE_ZH 覆盖测试扩展）。
5. npm build + 全部判据脚本 + cargo 全套 + 两条仓库门禁全绿。
