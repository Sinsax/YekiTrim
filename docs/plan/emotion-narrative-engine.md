# 情绪叙事引擎：把小剧场做成"可执行的演出"

> 立档：2026-10（提案，**未拍板、未动手**）。**这是 [`polish-enrichment-proposal.md`](polish-enrichment-proposal.md) 的"创新层"**——
> 那份讲的是"补齐零件"（文字元素、叙事角色、判据修正），**这份讲的是把这些零件编成一场演出**。
> 前置：先读 enrichment 那份的 §0 四条红线（尤其 **R1 出片只剩底座一条腿** 与 **R2 分工边界**）。
> 相关：`crates/yekitrim-core/src/danmaku/mod.rs`（弹幕信号）、`spec/effects.json`（效果权威）、
> `crates/yekitrim-polish/src/parse/text.rs`（已有的高亮/hook 雏形）。

---

## 0. 这份文档回答什么

用户要的是"**小剧场**"与"**更精细、有情绪指引**"—— 不是再加十个特效，而是让成片**像有人在导**。

本方案的立论是：

> **本仓已经有全套"零件"（字幕/贴纸/运镜/特效/音效），也已经有一个被完全浪费的"情绪信号源"
> （弹幕的颜色与文本）。缺的是把二者连起来的那一层：**
> **把"观众在什么时刻、以什么情绪"翻译成"画面该做什么"。**

这一层我叫它 **情绪叙事引擎（Emotion Narrative Engine）**。它由三件东西构成：

| 组件 | 一句话 | 依赖 |
|---|---|---|
| **① 情绪轨道**（Emotion Track） | 从**弹幕**反推每个时刻的"观众情绪"（不是条数） | 弹幕**可选**，缺失时降级 |
| **② 演出脚本**（Show Script） | 把"情绪 + 叙事角色"编成**一串有先后关系的画面指令** | 依赖 enrichment 的 `role` |
| **③ 演出节拍**（Beats） | 决定"什么时候该动、什么时候该静" | 纯规则 |

## 1. 为什么这条路是"新的"——三个今天完全没用的信号

我把 `danmaku` 模块读透了，结论是：**本仓的弹幕信号只用了 1/4**。

| 信号 | XML 里有吗 | 今天用了吗 | 能表达什么 |
|---|---|---|---|
| **条数** | ✅ | ✅ **只用了这个**（`analyze` 数中点） | 热度 |
| **文本** | ✅ | ❌ **完全丢弃** | **情绪内容**（"笑死""？？？""泪目"） |
| **颜色** | ✅ `p[3]` 已解析成 `#rrggbb` | ❌ **解析了但没人读** | **情绪强度**（B站彩色弹幕要花钱） |
| **模式** | ✅ `p[1]`（滚动/底端/顶端/逆向） | ❌ 只用来定 `y` | **情绪类型**（顶端/底端弹幕是"喊话"） |

逐条说清楚（都有代码依据）：

### 1.1 文本 —— 最富的一个，却完全没读
`parse_bililive_xml` 把 `text` 读进来了，但 `analyze` 只做 `counts[idx] += 1`。
**弹幕文本是全网最好的"观众情绪标注"** —— 而且是**免费的、时间对齐的**：
- 笑 → "笑死""哈哈""草"
- 惊 → "？？？""卧槽""啊？"
- 感动 → "泪目""绷不住了"
- 认同 → "确实""+1"

**B站弹幕文本 + 时间戳 ≈ 一份人工情绪标注数据集**，而本仓一条都没用。

### 1.2 颜色 —— 解析了，但没人读（**这是最可惜的**）
`parser.rs:13` 有 `color` 字段、`parse_bililive_xml` 也把它算出来了
（`format!("#{:06x}", color_dec & 0xFF_FFFF)`）—— 但**全仓没有任何消费者**。

而 B站的颜色是**花钱的**：
- **普通弹幕是白色**；
- **彩色弹幕需要"高级弹幕"权限或付费**（舰长/老爷）。

⇒ **一条弹幕的颜色 = 观众愿意为这条情绪付费**。
**这是"贵"的投票，比条数硬得多** —— 与开源实现 HotClip 的"花钱和动手的票比弹幕硬"是同一个道理。

### 1.3 模式 —— 只用来定 y
`default_y_for_mode`：4=底端(1000)、5=顶端(100)、其余=滚动(400)。
但**模式本身有语义**：**顶端/底端弹幕是"固定喊话"**（不是随手飘过），
通常出现在"我要说一句重点"的时刻。这个信号今天被降级成一个坐标。

## 2. 组件 ①：情绪轨道（Emotion Track）

### 2.1 产出什么

一条随时间的曲线，每秒一个（或每个窗口一个）**情绪向量**：

```
time        joy    shock  laugh  awe    (0~1)
12.0        0.1    0.8    0.3    0.6
12.5        0.2    0.9    0.4    0.7
```

**关键：不是"热度"，是"哪种情绪"。** 这是本方案与既有 `popularity` 的根本区别 ——
`popularity` 只知道"这里很热"，而情绪向量知道"**这里是震惊**"还是"**这里是爆笑**"，
**两者该配的画面完全不同**（震惊 → 定格/闪白/静音；爆笑 → 抖动/贴纸/音效）。

### 2.2 怎么算（三层融合，都可降级）

| 层 | 输入 | 方法 | 成本 |
|---|---|---|---|
| **L1 词表** | 弹幕文本 | 关键词表（笑/惊/泪/问号…），**中文 + 网络用语 + 颜文字** | 零成本，规则 |
| **L2 颜色/模式** | `color` / `mode` | 彩色弹幕、顶端/底端弹幕**加权** | 零成本（字段已有） |
| **L3 语义** | 弹幕文本 | **LLM 批量打标**（一批窗口一次调用，复用现有 LLM 链路） | 低（可选增强） |
| **补充** | 字幕文本 | 主播**自己**的情绪（语气词、感叹句）—— **弹幕缺失时的主判据** | 已有 ASR |

**L1 先行**：词表法零成本、可解释、可单测，**先做它就能拿到大部分价值**。
L3 是"锦上添花"，且**必须可选**（有用户不想花 token）。

### 2.3 无弹幕时怎么办（**硬要求**）

⚠️ **弹幕文件不一定存在** —— 这时情绪轨道**必须**退到"字幕情绪"，
并且**在日志里明说用了哪条判据**（不许静默降级，这是 enrichment §2.6 的同一条纪律）。

| 情形 | 情绪来源 | 日志 |
|---|---|---|
| 有弹幕 | L1+L2(+L3) 融合，字幕作补充 | `情绪轨道：弹幕 N 条 + 字幕 M 条` |
| **无弹幕** | **只用字幕**（语气词/感叹/句密度） | `⚠ 本次无弹幕信号，情绪轨道按字幕判` |
| 两者都弱 | 退化成"均匀"，**降低演出强度**（不是硬演） | `情绪信号弱，已降低演出密度` |

## 3. 组件 ②：演出脚本（Show Script）——"情绪 → 画面"的映射表

**这是本方案的核心。** 一张**声明式**的表，把"情绪 + 叙事角色"映射到"画面指令序列"。

### 3.1 为什么需要它（而不是让 LLM 自由发挥）

今天的流程是"LLM 逐段生成事件"。**它的上限就是 LLM 的想象力，且不可复现、不可调**。
而"情绪 → 画面"是**有成熟惯例的**（剪辑学 + 短视频工业界），应该**固化成表**，
让 LLM 只负责"**判断这里是什么情绪**"，不负责"**该配什么画面**"。

> 📌 **这正是本仓既有的分层哲学**：LLM 做**语义**，后处理做**确定性**。
> （`process` 全程无 LLM、幂等；`cap_pip_shots` 等守卫就是这个哲学。）**演出脚本是它的自然延伸。**

### 3.2 映射表（初稿）

| 情绪 | 叙事角色 | 画面指令序列 | 音效 |
|---|---|---|---|
| **震惊** shock | punch | ① 静音 0.2s（**先抽掉声音**）→ ② `flash` 白 → ③ `zoom` 近景 → ④ `text` 大字 | impact（落在 flash 那一帧） |
| **爆笑** laugh | punch | ① `shake` → ② 贴纸连出 → ③ `zoom` 轻微推 | 笑声/爆発 |
| **感动** awe | afterglow | ① `zoom` 拉远 → ② **留白**（不剪） → ③ `text` 小字 → ④ `fade` | 无 / 轻音 |
| **尴尬** cringe | punch | ① **画中画**（`zoom="远"`）→ ② 静音 → ③ `text`（"……"） | 蝉鸣/无 |
| **紧张** build | build | ① 缓慢推近 → ② 密度递增 → ③ 无强音效 | 渐入 |
| **认同** | setup | 不加特效（**留白**） | 无 |

⚠️ **`静音` 是怎么实现的**：本仓"画面归底座、声音归本仓"，音轨由 ffmpeg 混 ——
静音 = **在这段时间把原声压低/掐掉**，走 `[sfx]` 那套（**不需要底座改**）。
这可能成为**最有效的一条**："震惊"的标准手法就是**先静音再炸**（观众被"突然的安静"抓住）。

### 3.3 序列表（Beats）——决定"什么时候动"

⚠️ **这一条在 enrichment §4.2b 里已经查到数字**（视觉变化 3–6s、6s 硬上限；音效每 4–5s 最多一个）。
本组件把它**从"提示"升级为"编排"**：

```
t=0.0  [hook]     text 大字 + shake + 强音效        ← 抓人
t=1.2  [hook]     切回正片（硬切）
t=1.2-4.0 [setup] 无特效，字幕为主                  ← 留白，为对比蓄力
t=4.0  [build]    zoom 缓慢推近 1.3→1.5
t=6.5  [punch]    静音 0.2s → flash → zoom 近 → text
t=8.0  [afterglow] zoom 拉远 + 留白（不剪！）
```

**节拍器（Metronome）规则**：
- **两次"视觉变化"至少间隔 0.8s**（否则读作噪声）；
- **"静"的段必须有**（`setup` 段配额为 0）—— **没有静就没有动**；
- **爆点前后各留一口气**（前 = build，后 = afterglow）。

## 4. 组件 ③：把小剧场做成"一场戏"—— 三种可选的形态

"小剧场"有三种越来越"重"的形态，**建议按此顺序**：

### 形态 A：单段演出（**最小可用**）
一个切片内，按"情绪 + role"编排。**就是上面 §3 的全套**，不需要新概念。

### 形态 B：幕结构（章节）
给 `Segment` 加 `act`（幕），让切片**分成几个"幕"**，每幕有自己的情绪走向：

```
第一幕：日常闲聊（setup）      → 平静
第二幕：话题转向（build）      → 升温
第三幕：翻车爆发（punch）      → 爆点
```

产出：**章节卡**（`text style=chapter`）+ 每幕开头的**幕标**。
这直接对上外部调研里的「チャプターが始まるタイミングで大きく文字を出すカットイン」。

### 形态 C：角色化演出（**最有想象力的一层**）
把"情绪指引"**人格化成角色**：一个**贯穿全片的"旁白/吐槽役"**。

| 做法 | 说明 |
|---|---|
| **吐槽字幕** | 用 `text` 在关键时刻出现"旁白"（"这已经是第三次了…"） |
| **固定位置 + 固定风格** | 让观众认得出"这是那个吐槽角色" |
| **计数/积累** | "第 3 次""5 连败" —— 与 §3.2 的 `count` 样式配合 |

⚠️ **但有合规红线**（外部调研明确查到）：
- **不要加原创旁白解说**（改写语义）—— hololive 规约要求"尊重原作者本意"，
  且明禁"単なる改変の域を出ないもの"；
- 吐槽字幕必须**基于主播自己说过的话**（引用/概括），不能编造观点。
⇒ **产品口径**：`text` 只做"**把主播的话挑出来放大**"，**不做"替主播说话"**。
这条要写进 LLM 提示词。

### 4.1 形态 D（更远）：多片段合集
把多个切片拼成一条"剧场"，统一片头/片尾。见 enrichment §4.4 —— **不建议先做**。

## 5. 与 enrichment 那份的关系（别重复建设）

| enrichment 那份 | 这份 |
|---|---|
| §2.2 `elements`（`text`/`sticker`） | **是这份的零件库** —— 没有 `text` 就没有"吐槽字幕" |
| §3 `Segment.role` | **是这份的骨架** —— 没有 `role` 就没有"幕" |
| §2.6 多信号爆点判据 | **是这份的简化版** —— 这份把它升级成"情绪向量" |
| §3.4 静默保护 | **被这份复用** —— "震惊/尴尬"的配方里就有静音 |
| §5 落地顺序 | **这份排在它之后**（零件先齐，再编排） |

> ⚠️ **所以：不要跳过 enrichment 直接做这份。** 但**设计上可以现在就定**（本文档的用途）。

## 6. 落地顺序

| 阶段 | 内容 | 出口判据 |
|---|---|---|
| **E1** | **情绪轨道 L1（词表法）** | 合成弹幕单测（"笑死"→ joy/laugh 高、"？？？"→ shock 高）；无弹幕工程不崩、日志明说 |
| **E2** | **颜色/模式加权（L2）** | 单测：彩色弹幕权重 > 白色；顶端/底端弹幕另计 |
| **E3** | **演出脚本（`role` × 情绪 → 指令）** | 表可单测；同一输入两次跑**结果一致**（确定性） |
| **E4** | **节拍器（Beats）** | 间隔守卫单测（视觉变化 <0.8s 被拦、`setup` 段配额 0） |
| **E5** | **形态 B 幕结构** | `act` 字段 + 章节卡 + 老工程零迁移 |
| **E6** | 形态 C 角色化演出 | LLM 提示词带合规红线 + 单测 |
| **E7** | L3 LLM 情绪打标（可选） | token 用量可见、失败可降级 |

⚠️ **每一条都必须能"没有弹幕也跑"** —— 这是本方案的**硬前提**（§2.3）。

## 7. 待拍板

| # | 取舍 | 建议 |
|---|---|---|
| 1 | 情绪分类用几类 | **先 5 类**：笑 / 惊 / 感动 / 尴尬 / 平静（再多难标、难验证） |
| 2 | L3（LLM 打标）是否默认开 | **默认关**，用户显式开（token 成本 + 要能降级） |
| 3 | "静音"作为情绪手法的接受度 | 这是"震惊"最有效的手法，但会**突然没声** —— 可能有人不喜欢，建议**做成可关** |
| 4 | 形态 C 的吐槽角色 | **产品红线**：只"放大主播的话"，**不替主播说话**（合规） |
| 5 | 情绪轨道是否入库/落盘 | 建议落 `<工程>/data/emotion.json`（可复算、可手改、可诊断） |

## 8. 一句话

**把已经解析却没人读的弹幕"颜色 + 文本 + 模式"变成一条情绪曲线，
再用一张确定性的"情绪 → 画面"表把它演出来** ——
LLM 只判断情绪，**画面由表决定**。这就是"小剧场"与"情绪指引"的可执行形态。
