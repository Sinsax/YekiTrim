# 范式四：把剪辑变成"可对话的决策"，把音乐变成"节奏骨架"

> 立档：2026-10（提案，**未拍板、未动手**）。**第四份，与前三分是不同维度。**
> [`polish-enrichment-proposal.md`](polish-enrichment-proposal.md) 问"加什么零件"、
> [`emotion-narrative-engine.md`](emotion-narrative-engine.md) 问"按什么情绪演"、
> [`editing-decision-layer.md`](editing-decision-layer.md) 问"怎么剪"。
> **这一份问的是更根本的两件事：谁来决定、以及用什么当节拍骨架。**

---

## 0. 这一份的两个"新轴"

前三份文档都在**同一根轴**上加深：*"系统自动决定一切，越做越精细"*。
本份提出**两根正交的新轴**，它们都不是"更多效果"：

| 新轴 | 一句话 | 依据 |
|---|---|---|
| **轴 A：语言即界面** | 用户不说参数，说**意图**（"做一条巴黎之旅"）；系统**出计划**、用户**逐条批准**、再执行 | LAVE（Meta + UofT + UCSD，[ACM IUI 2024](https://www.dgp.toronto.edu/~bryanw/lave)，[arXiv 2402.10294](https://arxiv.org/abs/2402.10294)） |
| **轴 B：音乐即骨架** | **先定音乐、再由音乐的节拍决定画面切在哪**（不是先剪画面再配音） | CutClaw（[HF 2603.29664](https://huggingface.co/papers/2603.29664)，多智能体 + 音乐同步） |

**为什么这两根轴算"创新"**：前三份文档里，**决定权始终在系统**、**节拍始终来自内容**。
这两根轴各自改变了一个前提。

## 1. 轴 A：语言即界面（plan-and-execute + 人批准）

### 1.1 LAVE 做了什么（值得抄的部分）

它的交互是：

```
用户： "make a video for my trip to Paris"     ← 一句话意图，不是参数
  ↓
系统： 产出一个 **action plan**（一串剪辑动作，每个带 context）
  ↓
用户： **逐条 review & approve**（可以改、可以否、可以插入新指令）
  ↓
系统： 把批准的动作翻译成真实函数调用并执行
```

**关键设计（三条，都很值得抄）**：

| # | 设计 | 说明 |
|---|---|---|
| 1 | **计划与执行分离** | 计划是**可读的**（用户看得懂"我要做什么"），执行是确定性的 |
| 2 | **逐个批准** | 人保留否决权，不是"一键生成、不满意重来" |
| 3 | **解释理由** | ⚠️ 原话："For transparency, the LLM also **explains its rationale** for the trimmings, detailing how they align with user instructions" |

**第 3 条是最被低估的。** 本仓今天所有自动决策**都不解释** ——
用户看到切好的片子，**不知道系统为什么这么切**。而"能问为什么"恰恰是从"工具"变成"合作者"的分界。

### 1.2 对本仓的映射（**这是重点**）

本仓今天已经有**合适的地基**，只是没往这个方向用：

| LAVE 的能力 | 本仓的对应物 | 状态 |
|---|---|---|
| Footage overviewing（给素材生成主题概览） | `Segment.note`（"这段在讲什么子话题"） | ✅ **已有** |
| Storyboarding（按叙事排序） | `Segment` 的**时间序**（今天只有一个顺序） | ⚠️ 有数据、没当决策 |
| Video retrieval（语言检索素材） | `Skill: yekitrim-topic-scan`（按话题搜全部字幕/弹幕） | ✅ **已有**（但只在对话里用） |
| Clip trimming（自然语言裁剪） | `Segment.start/end` + `mute_ranges` | ⚠️ 只能拖，不能"说" |
| **Rationale（解释理由）** | ❌ **完全没有** | 缺 |

⇒ **本仓离"语言即界面"其实只差一层包装**：把已有的 `note` / 检索 / 边界决策，
变成**可读的计划 + 理由**，再接一个对话入口。

### 1.3 具体形态建议

```
用户： "把这场直播做成 3 分钟的搞笑合集，开头要炸"

系统（plan，可读、可改）：
  ① 找爆点        → 命中 7 处（弹幕峰值 + 情绪词），按强度排序
  ② 选开头        → 建议从 04:12 开始（爆点前 3 秒，句末）  [理由：不切断句子]
  ③ 选结尾        → 建议到 12:48（笑点后的留白结束）      [理由：保护喜剧节拍]
  ④ 删减          → 建议删 6 段（共 4 分 12 秒）          [理由：离题/拖沓]
  ⑤ 演出          → 7 处爆点配"爆笑"配方（抖动+贴纸+推近）
  [批准全部] [逐条看] [改：开头再早 2 秒]
```

**用户批准后才执行** —— 而且 `[改：开头再早 2 秒]` 这种**自然语言微调**是天然支持的
（因为计划是结构化的，改一条就是改一个字段）。

⚠️ **与既有架构的关系**：这不是替换 `polish.toml`，而是**在它上面加一层"计划"**——
计划批准后**落成** `polish.toml` 的字段（`segments` / `mute_ranges` / 新增的 `[editing]`）。
**所以它与前三分文档完全兼容。**

## 2. 轴 B：音乐即骨架（先定音乐，再定切点）

### 2.1 CutClaw 的核心洞察

> *"a **Playwriter Agent** orchestrates the whole storytelling flow and structures the long-term narrative,
> **anchoring visual scenes to musical shifts**."*
>
> *"...produces videos with synchronized music... **rhythm-aligned** videos."*

**它把因果关系倒过来了**：不是"剪好了再配乐"，而是
**"音乐的结构决定了画面的切点"**。

**为什么这是对的**（常识层面）：所有卡点视频、所有短视频的"节奏感"，
本质都是**画面的切换落在音乐的节拍/段落上**。观众感到"爽"，是**视听同步**带来的。

### 2.2 ⚠️ 本仓完全没有这个轴（已核实）

我查过了：

| 项 | 本仓状态 |
|---|---|
| **BGM 支持** | ❌ **完全没有**。全仓没有任何"背景音乐"概念（只有 SFX） |
| 音乐节拍分析 | ❌ 没有 |
| 响度曲线 | ✅ **有**（`measure_loudness_curve_cached`，出片页与混音共用；`ebur128`） |
| 混音 | ✅ **有**（`Ffmpeg::mix_sfx`） |

⇒ **技术地基齐全（有响度分析、有混音），缺的是"音乐"这个层级。**

### 2.3 建议的形态

```
① 选/指定 BGM（用户给文件，或从素材库选）
② 分析音乐结构  → 节拍（beat）/ 段落（intro/verse/drop/outro）/ 强拍位置
③ 排演出        → 把"爆点"对齐到"强拍/段落变化"，把"铺垫"放在低能量段
④ 出片          → 画面切点由音乐决定，音轨混入 BGM（带 ducking）
```

**这一步能带来的、前三份给不了的**：

| 效果 | 说明 |
|---|---|
| **卡点** | 爆点切在强拍上 —— 这是"爽感"的本质 |
| **段落对齐叙事** | 音乐进副歌 = 进爆点；音乐渐弱 = afterglow |
| **节奏不平均** | 今天本仓的节奏来自内容（每段配点东西），音乐会**强制**出"快慢对比" |

⚠️ **但有一条硬约束**：本仓**音轨归自己**（`--no-audio`，声音由 ffmpeg 混入）——
所以 BGM 的接入点在**本仓 ffmpeg 混音这一侧**，**不需要底座改**。✅ 这条路走得通。

> ⚠️ **合法性提醒**（照实写）：BGM 涉及版权。建议**只支持用户自带文件**，
> 或接已有的素材库机制（照贴纸库/音效库的先例），**不自带任何音乐文件**。

### 2.4 与"静音"的关系（一个有意思的交叉）

`emotion-narrative-engine.md` 里"震惊 = 先静音再炸"是纯内容手法。
**有了音乐骨架，静音多了一层含义**：**把音乐也抽掉**（不只是原声）。
"drop 前的一拍空白"是电子乐最经典的张力手法 —— 而这**正好能被自动生成**（在段落边界处做）。

## 3. 这两根轴为什么比"再加效果"更值

| 维度 | 前三份文档 | 本份 |
|---|---|---|
| **决定权** | 全在系统 | **人可逐步介入**（轴 A） |
| **节拍来源** | 内容（字幕/弹幕） | **音乐**（轴 B） |
| **可解释性** | 无 | **每个决策有理由**（轴 A） |
| **用户能力上限** | 看结果、拖时间轴 | **说意图** |

> 📌 一句话：**前三份是"把自动剪辑做得更好"，这份是"让剪辑可以被讨论、被指挥、被卡点"。**

## 4. 与其它三份的关系与顺序

```
决策层（怎么剪） → 演出层（怎么演） → 零件层（用什么演）
       ↑
  本份轴 A：把上面每一层都变成"可读、可批准、可改"的计划
  本份轴 B：给上面每一层提供"音乐节拍"这个外部骨架
```

**本份不是"第四个阶段"，而是横切在前三层之上的两件事。**

建议的落地顺序（**轴 A 优先**，因为成本低、收益广）：

| 阶段 | 内容 | 为什么 |
|---|---|---|
| **N1** | **决策理由（rationale）** —— 每个自动决策带上"为什么" | **不需要任何新架构**，只要在现有决策点记一个 `reason`。**这是全案性价比最高的一项** |
| **N2** | **计划视图**（把 `[editing]` + `segments` 渲染成可读计划，可批准/否决） | 依赖 `editing-decision-layer.md` 的 `[editing]` 结构 |
| **N3** | **自然语言微调**（"开头再早 2 秒"） | 依赖 N2 的结构化计划 |
| **N4** | **BGM 接入 + 混音**（不带卡点，只做背景音乐 + ducking） | 音轨侧，本仓可控 |
| **N5** | **音乐结构分析 + 卡点** | 需要节拍检测（可先用现成库） |

---

## 5. 明确"不做/暂缓"

| 项 | 理由 |
|---|---|
| **多智能体架构**（CutClaw 的 Playwriter/Editor/Reviewer） | 那是为了**跨小时级素材**的长时程规划；本仓处理的是**单切片**（分钟级），**引入多智能体是过度设计**。抄它的**洞察**（音乐即骨架），**不抄它的架构** |
| **自带音乐文件** | 版权。只支持用户自带 / 素材库 |
| **AI 生成 B-roll / 生成视频**（LAVE 的未来方向） | 与本仓"忠于原片"的定位冲突 |
| **主动介入式 agent**（LAVE 自己也在警告） | 原话："agents that proactively engage without solicitation can be perceived as **intrusive**" |

---

## 6. 结论

前三份解决"**剪得更好**"，这份解决"**剪得可商量、剪得有节奏**"：

1. **轴 A（语言即界面）**：本仓离它**只差一层包装** —— 因为 `note` / 话题检索 / 边界决策**都已经有了**，
   缺的只是"把它们变成可读、可批准、**带理由**的计划"。
   ⭐ **其中"决策理由"（N1）不需要任何新架构，建议立刻做** ——
   今天用户完全不知道系统为什么这么切，这是"工具"与"合作者"的分界。
2. **轴 B（音乐即骨架）**：本仓**零基础**（连 BGM 概念都没有），
   但**地基齐全**（响度分析 + 混音都在），且**音轨归本仓 ⇒ 不需要底座改**。
   "爆点切在强拍上"是短视频爽感的本质，而本仓今天完全没有这个轴。
