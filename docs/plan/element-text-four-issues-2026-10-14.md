## 一 · 四个问题：真因与方案

### ① 元素位置不对 —— **预览**把"盒左上角"当成了绘制原点，还**丢了 `pos`**

**两条独立的错，都在预览这条链上。**

#### 1a `x`/`y` 是「盒子左上角」，预览当成了文字自身的左上角

`process` 写回的 `x`/`y` 语义（`process/placement.rs:1124`）：

```rust
pub struct Pick {
    /// 贴纸盒子左上角（帧像素）。
    pub x: f64,
    pub y: f64,
```

`layout_text_elements` 写的就是它（`process/mod.rs:677`）：
`*x = Some(pick.x_pct(f)); *y = Some(pick.y_pct(f));`

而预览直接把它当 `left`/`top` 用（`PolishPreview.vue:55`）：

```html
:style="{ left: tx.xPct + '%', top: tx.yPct + '%', ... }"
```

`.text-el` 是 `position:absolute`（`:3539`）⇒ `left/top` 定位的是**元素自身左上角**。
⇒ 底座算的"盒子左上角"被当成"文字左上角"直接落笔，
**差的正是盒子与文字之间那段（居中留白 / 多行上限 3 行 / 底部留白）**。

> ⚠️ 盒子尺寸在 `TextLayout::solve` 里是**按下限/上限**算的，与真实文字块不同 ——
> 所以这个偏移**逐档不同、且随文字长短变化**，不是"整体挪一点"。
> 这正是用户看到"位置不对"却说不清偏多少的原因。

#### 1b **`pos` 在预览里被整条丢掉**（已实测确认）

`entry.textPos` 在 `engine.js:429` 被算出来了：

```js
entry.textPos = String(ev.pos ?? '').trim().toLowerCase() || 'bottom'
```

`engine.js:2169` 也把它写进了输出（`pos: e.textPos`），
**但 `PolishPreview.vue` 从头到尾没用过它**：

```
$ grep -c "tx.pos\|\.pos\b" webui/src/components/PolishPreview.vue
0
```

（文件里唯一命中 `pos` 的 `posPct` 是**字幕**那条路的，与元素无关。）

⇒ 「上 / 中 / 下」三档在预览里**完全同形**。
用户在面板上换档位，预览**纹丝不动**——而这不是"位置略偏"，是**这一维整个没接上**。

#### 1c `transform-origin` 绕"元素中心"，而底座绕"**盒子**中心"

`.text-el`（`PolishPreview.vue:3539-3546`）：

```css
.text-el { position:absolute; white-space:pre; line-height:1.15;
           transform-origin:center center;   /* 元素自己的中心 */ }
```

注释说「与 Dhampir 的 `blit_affine`（`c_src = 位图中心`、`c_out = 落点中心`）同口径」——
**但底座的位图就是那个盒子**（`TextLayout::solve` 的 `box_size()`），而预览的元素
**只是文字本身**（`white-space:pre` 的紧贴盒）。两者尺寸不同 ⇒ **旋转/压缩的支点不同**。

⇒ 倾斜、压缩这类"绕中心转"的档，预览与成片**在同一个档位上转出不同结果**。
这与 1a 是**同一个根因**（预览不知道盒子的尺寸与位置），所以**同一个方案能一起解决**。

#### 方案（1a + 1b + 1c 一起）

**唯一的正确做法：预览不该自己摆，应该问底座"这块字画在哪"。**
但预览走的是 wasm、且**没有 `layout()` 的导出**（见下面 ② 的同一处缺口）。

两条路，**推荐 B**：

| | 做法 | 影响范围 | 代价 |
|---|---|---|---|
| A | 在前端**复刻** `TextLayout::solve` 的盒尺寸公式，把左上角换算成文字原点 | `engine.js` + `PolishPreview.vue` | **第 N 份实现**（模板/`canvas.js`/`timeline.rs`/`engine.js`/转译器已是 5 份）—— 本仓反复吃过这份苦 |
| **B** | **请底座 wasm 导出 `text_layout`**（或让 `pos` 走一个已存在的路径），前端只读结果 | 底座 + 前端 | 跨仓一次；但**只有一份实现** |

⚠️ B 需要底座改动 ⇒ **要单独约**（本仓不许加 GPU 管线，而这是"导出已有纯函数"，不违反）。

**立即可做的止血（不等底座，也不新增实现）**：预览**优先用 `pos`**——
`pos` 是**语义档位**（上/中/下），不需要盒尺寸就能摆；`x` 只用来定**水平**：

```
top    → 上边距 MARGIN，水平按 x
center → 垂直居中，水平按 x
bottom → 沿用现状（贴底）
```

这能让 1b **当场可见**（换档位预览就动），1a 的残余偏移等 B 落地。

### ② 元素出现时「字幕的描边和字体变成默认的」—— **已定位到确切的代码行**

上一轮我查到的是"元素轨少写 `font_family`/`shadow_*`/`line_height`"——**那是对的，但只对了成片那条腿**。
预览这条腿走的是**另一条完全不同的路**（元素 ASS → 底座 libass）。

**实证**（dump 出那份 ASS 的 `Style:` 行）：

```
$ grep '^Style:' .workbuddy/prev-bug/p/dhampir-text_hook_center_pink.ass
Style: Default,Sans,80,&H00C080FF,&H000000FF,&H00000000,&H80000000,0,0,0,0,100,100,0,0,1,2,1,2,10,10,10,1
              ^^^^
```

对照 ASS 字段名：

| 字段 | 值 | 应当是什么 |
|---|---|---|
| `Fontname` | **`Sans`** | `Noto Sans SC`（字幕那支）—— **这就是"字体变成默认的"** |
| `Outline` | `2` | 与元素的描边口径对齐（目前是硬编码常数） |
| `OutlineColour` | `&H00000000` | 同上（硬编码） |
| `Shadow` | `1` | 同上（硬编码） |

**病根 = 转译器 `tools/polish-to-dhampir.mjs:6640`**：

```js
{ font: 'Sans', fontSize: st.fontPx, danmaku: false },
```

⚠️⚠️ **这是本仓第 ② 类老病「两个消费方，只迁了一个」的又一例**，而且**铁证就在同一个文件里**：
上面 6103 行附近的**弹幕**那条路，早就因为同一个坑被修过，注释还写着：

```
//    这里**曾经写 `'Sans'`**，而上面 `font_family` 的注释还写着"空值填成字幕那支"
//    —— 两行自相矛盾，实际结果是**预览用字幕字体、成片用 Sans**（不一致且不报错）。
//    `'Sans'` 也不是"系统无衬线"的可靠表达：libass 认不出就静默落 ArialMT。
font: dmStyle.font || DEFAULT_DANMAKU_FONT,
```

**弹幕改了，元素没改** —— 而元素的症状更具迷惑性：libass 认不出 `Sans` **不报错**
（`lines_failed: 0`），只是换了个字体画 ⇒ 用户看到"字幕的字体和描边变成默认的了"。

#### 方案

1. **`font: 'Sans'` → 与字幕同源的族名**（`fontFamilyFor(subStyle.font)`，即 `Noto Sans SC`）；
2. `Outline`/`OutlineColour`/`Shadow` 三个硬编码常数 → 与字幕那份 ASS 同源（见 ③ 的口径）；
3. ⚠️ **加一条跨产物判据**：元素 ASS 的 `Fontname` 必须**不等于** `'Sans'`，
   且必须等于字幕侧的族名 —— 「写了 `Sans` 也不报错」正是它能存活至今的原因。
   **光靠这条不够**（`Sans` 是个合法字符串），判据要钉**取值的来源**
   （与弹幕那处一样：`fontFamilyFor(...)` 的产物），否则下一个人换个别的假族名照样过。

**影响范围**：`tools/polish-to-dhampir.mjs`（一行取值 + 三个常数）+ 新判据 + 重建。
**这是四个问题里最便宜、最有把握的一个**。

## 二 · 两轴档位收敛（用户指定的目标清单）

### 目标（用户口径，逐字）

**形态（样式）只保留 4 项**：
`默认` · `倾斜` · `竖排` · `弧形（扇形）`

**动效只保留**：
`默认弹出` · `抖动` · `淡入淡出` · `斜向砸入` ·
**逐字变化（合并为一个动效）**：`逐字变大` · `逐字变小`

### 现状 → 目标映射（档数已逐档点清）

现状 **39 档**（`tools/polish-to-dhampir.mjs:3261` 的 `ANIM_PRESETS`，权威表）：

| 现状族（档数） | 目标归属 |
|---|---|
| （无）`none` 不设/清除 | **默认** |
| `tilt` 倾斜 **3** | **倾斜** |
| `vtext` 竖排 **3**（`vtext_thin/bold/shrink`） | **竖排** |
| `arc` 逐字弧形 **3** | **弧形（扇形）** |
| `pop` 弹出 **3**（`pop_std/soft/perchar`） | **默认弹出** |
| `shake` 抖动 **3** | **抖动** |
| `shrink_in` 收缩 **2** + `fade_only` **1** | **淡入淡出**（⚠️ 现无"淡入"，见待确认 3） |
| `slam` 砸入 **3** | **斜向砸入**（⚠️ 现无"斜"这一维，见待确认 2） |
| `size` **3** + `grow` **3** + `shrink` **3** + `hop` **3** + `scatter` 族 **3** | **逐字变化** ⇒ **逐字变大 / 逐字变小** |
| `sway` 摇摆 **3** | **删除**（不在目标清单） |

**合计 39 → 约 4（形态）+ 6（动效）≈ 10 档**，删掉约 **29 档**。

⚠️ **待用户确认 3 点**（我不猜）：
1. **`sway` 摇摆**整条删除 —— 存量工程里选了它的会变成"认不出的档名"（现状 UI 会显示"未知档"并保留原值，不丢数据）。确认可接受？
2. **「斜向砸入」**= 现有 `slam_std/lg/squash` 改角度，还是**新档**？「斜向」的角度是固定（如 30°）还是可调？
3. **「淡入淡出」**：现有 `shrink_in_*` 是"收缩 + 淡出"，**没有淡入**。是"补上淡入、去掉收缩"，还是"只淡出"？

### 合并「逐字」那一族的方案

用户口径：**合并成一个动效下辖两个**（逐字变大 / 逐字变小）。

⚠️ 这两档**必须真的产出不同观感**——本仓有过"两个预设输出逐字节相同"的教训
（`8d7db04` 的 `vtext_thin` 与 `vtext_bold`）。合并时**逐档验证像素/参数不同**。

**影响范围**（收敛 = 删档 + 改档名 + 迁存量值，是全仓最贵的一类改动）：

| 位置 | 影响 |
