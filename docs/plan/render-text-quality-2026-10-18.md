# 成片文字质量排查（2026-10-18）

> 触发：用户报「渲染导出：弹幕和字幕有模糊和锯齿（图1/3 导出、图2/4 预览）」「弹幕时间没应用偏移」
> 「检查一下文字层」。样本片段：项目 10 / 小时候偷茶踩人家坟头…

## 一、已修：**描边口径**（真缺陷，底座 `3f45538`）

预览走 CSS `-webkit-text-stroke`（**居中**：w/2 在外、w/2 在字形内），
底座是 `ring_of(dilate(fill, w), fill)`（**全在外侧**）⇒ 同一个 12px，成片的墨是预览的**两倍**。
用户截图里"成片白环明显更粗、字被粗边吃掉"即此。

改法：新增 `erode_disc`，内圈描边 = `ring_of(dilate(fill, ceil(w/2)), erode(fill, floor(w/2)))`。
判据 `centered_stroke_tests`（20x20 方块 + 8px ⇒ 外扩 4 / 内缩 4，含变异自证）。
外圈（白环）不动：它本来就是"在描边之外再扩"。

## 一点五、已修：**锯齿**（底座 `56c6304`）

描边与白环都来自 `dilate_disc(fill, r)`（圆盘邻域取**最大**覆盖度），而圆盘偏移是**整数**的
⇒ 外缘落在离散位置上：直边是整像素台阶、45° 斜边是锯齿。

改法：新增 `dilate_aa`（+`coverage_distance` 两遍 chamfer 距离场），覆盖度 = `max(原覆盖,
`(r + 0.5 − 距离) × 255`)` ⇒ 边界像素拿到中间值（与 libass 画字形同一种抗锯齿）。
描边与白环的两条边都换成它。判据 `dilate_aa_makes_a_soft_rim`（变异：斜坡换成硬阈值 ⇒ 红）。

A/B（同一帧同一段字幕 2×）：改前描边边缘呈波浪、字腔被啃；改后轮廓干净、白环更匀。

### ⚠️ 同时回滚的两轮实验

1. **居中描边**（外 ceil(w/2) + 内 erode(floor(w/2))）：暗描边**向内吃字形一圈** ⇒ 用户看到
   「第一层描边坏了/消失」。⚠️ 而且这条修改的**前提本身就错**：转译器的
   `stroke_ratio = strokePx / 2 / height` **已经**把 CSS 的居中折算成「外侧一半」了 ⇒
   原几何（全在外侧）与预览的外缘**本来就一致**，不该再减半。
2. **描边改用 libass 轮廓**：暗像素 1236→3078，一团黑块。

## 二、两条被**证伪**的假设（别再照着改）

### ① "位图被二值化了 ⇒ 锯齿"

**错，是我量错了**：`DHAMPIR_DUMP_RASTER` 写的是**预乘 RGB**，覆盖度在 **alpha**，而 PPM 没有 alpha
⇒ 看上去"全 255"。探针实测 `fill_plane`：**ink=3452 / 中间调=2585（75%）** ⇒ 抗锯齿一直都在。

### ② "动画文字（pop/心跳/逐字）走 blit_affine 双线性 ⇒ 发虚"

**错**：`text_overlay.rs:1101` 明写 `font_ratio`「**求值层已把动画缩放乘进来**」⇒ 栅格化是**按动画后的尺寸**做的，
每个缩放档自己一张位图，**不经重采样**。`blit_affine` 只服务 **T3 倾斜/压扁**（rotation + 逐轴 squash）。

那次"41 vs 957 锐边像素"的测量**有混淆**：0.6 缩放时字形面积只有 36%、且 1px 抗锯齿带占的比例更大
⇒ "极锐梯度像素"自然变少，**不是糊**。样本工程 T3 命中 **0 处**。

## 四、还剩的已知偏差（未修，代价明确）

- **T3 倾斜/压扁**走 `blit_affine` 双线性：旋转/压扁的字会比 DOM 预览软一点（预览是矢量每帧重画）。
  真要修 = 给旋转档做超采样（2× 栅格化再缩），代价是位图内存 ×4。
- **描边的几何**仍是"圆盘膨胀"：外缘跟着圆盘走，45° 拐角会比 libass 的轮廓描边**圆一点**。
  要更准就得**再起一次 libass 遍**（`PrimaryColour` 透明 + `OutlineColour` 白 ⇒ 只有描边、且带 libass 抗锯齿），
  代价 = 每行多一次 ffmpeg（2026-10-16 正是为省这一次才改成膨胀的）。
  ⚠️⚠️ **2026-10-18 真做了这一版，A/B 后撤回**（底座仓那一笔只留注释）：同一帧、同一段文字，
  描边的暗像素 **1236 → 3078**，肉眼是「一团黑块贴在字后」。原因是 libass 的 `Outline`
  并非「从轮廓往外扩 half」那套几何（还与 `FontSize` 联动，且 `ass_outline_px` 的 PlayRes
  补偿会再放大一次），叠加腐蚀出的内半边就是「又粗又糊」。**结论：保留膨胀/腐蚀** ——
  拐角略圆但粗细对得上；要再试**先做 A/B**。

## 三、已修：**编码侧**（2026-10-18，底座 `encoder_args` + 本仓 `cut_ranges`）

### 怎么定位的

用 **lossless PNG**（`dhampir frame`）与**成片解码帧**逐像素对比，把"渲染"与"编码"分开：

| 对比 | 结果 |
|---|---|
| lossless 的描边外缘扫描线 | 3~4px 平滑过渡 ⇒ **渲染侧抗锯齿已经在了** |
| lossless ↔ 成片解码（文字区 180x80） | **MAE 4.40 / max 51**，损伤全在字形边缘、带 4:2:0 色度污渍 |
| 5× 放大看到的"方格" | 是 1080p 像素栅格本身，不是渲染缺陷 |

⇒ 继续优化渲染层没有收益，剩下的差距全在**编码**。

### 改了什么

| 位置 | 改前 | 改后 |
|---|---|---|
| 底座 `pipeline.rs::encoder_args` | `-preset veryfast -crf 20` | **`-preset slow -crf 17`** |
| 本仓 `render/ffmpeg.rs::detect_encoder`（`cut_ranges` 用） | NVENC `p1/cq22`、libx264 `veryfast/crf22` | NVENC **`p5/cq19`**、libx264 **`slow/crf17`**（与第一遍同级，不做"更差的第二遍"） |

`-c:v libx264` / `-pix_fmt yuv420p` / `+faststart` **一项没动**（444 会破坏播放器与硬解兼容性）。

### 代价（同一 180 帧、1080p、只换参数）

| 设置 | 编码耗时 | 体积 | 文字区 MAE |
|---|---|---|---|
| `veryfast/crf20`（旧） | 528 ms | 156,558 B | 3.72（不过） |
| `slow/crf20`（只升 preset） | — | — | 3.46（不过） |
| `slow/crf18` | 957 ms | 273,222 B | 未测 |
| **`slow/crf17`（现在）** | **978 ms（1.85×）** | **291,048 B（1.86×）** | **2.59 ✓** |

⚠️ **体积接近翻倍**是这条改动最实在的代价。想省体积就把 `crf` 提到 18/19（一行改动），
然后用 `node scripts/check-export-text-quality.mjs ...` 看还能不能过 —— **判据会给出数字，不靠感觉**。

### 判据

`scripts/check-export-text-quality.mjs`（验收工具，不进 CI）：
`dhampir frame` 出无损 PNG → `dhampir render` 出 1 帧 mp4 → ffmpeg 解成灰度 → 量 **MAE / max / Δ>40 占比**。
阈值 **mae 3.0**（新参数 2.59 过、旧参数 3.72 **不过** —— 这组数字是**变异自证**跑出来的）。
`--self-test` 用合成缓冲自证判据能分辨 0 / 2 级 / 128 级差异。
