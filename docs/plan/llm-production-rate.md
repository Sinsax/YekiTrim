## 4. ⚠️ 温度 0 下的确定性：**不确定**

**实测：同一工程、同一素材、同一配置（temp=0, seed=42），三次结果不同：**

| | run1 | run2 | run3 |
|---|---|---|---|
| segments | 5 | **7** | 5 |
| element | 8 | 9 | 7 |
| sfx | 7 | **13** | 7 |
| 分段边界 | — | **不同** | — |

**⇒ "温度 0 = 确定性"在本环境不成立。**
**推断**（标明为推断）：该中转站/模型的 `thinking` 开启
（配置 `[llm.extra_params.thinking] type = "enabled"`），
且 `seed` 未必被上游真正采纳；也可能是并发窗口调度（`max_concurrent = 3`）
导致同样的输入在不同批次里被组合。**本轮未做对照实验去定位原因。**

**⇒ 对结论的影响**：**产出率是"稳定非零"，但具体数字不可复现**。
所有比较都应在**同一次运行内部**做（本文 §2 的对照组同理）。

## 5. 结论

### 5.1 `element`（§5 E5）—— **稳定产出，不是 0**

**三次实测 8 / 9 / 7 条，覆盖 15/17 段（88%），从未为 0。**
⇒ **本轮任务书假设的"可能根本不产"被实测推翻。**

**"只有上限无下限"确实存在**（`segment.rs:113` 只写"⚠️ 整段**最多** 1~2 条"），
**但它并没有导致不产** —— 与 `punch`（`:363`「整片**至少要有一段**」，实测 1/1/1 生效）相比，
**两者都在产**，只是**下限词的约束力更强**（punch 每次恰好 1 条，element 1.29~1.6 条）。

**⚠️ 反面读数（值得注意）**：`最多 1~2 条`这个**上限并没有被严格守住** ——
run1 有段产 2 条（合规），但**"每段"的口径下均值 1.6**、且**无一段低于 1**。
⇒ **上限词是有效的**（没有出现"整片都是大字"），**但它是"软上限"**（未逐段硬卡）。

### 5.2 `zoom="特写"`（§18-A）—— **确认 0**

**三次实测全 0**（`中`/`近`/`远` 各若干，从未出现「特写」）。
⇒ **与预测一致**：提示词 `segment.rs:83` 只教 `"远"/"中"/"近"`，
**LLM 不会自创未教的枚举值**。
**这是"词不存在 ⇒ 产出 0"的干净证据**（且 LLM 并非不会写 `zoom`——它写了 20/19/21 次）。

### 5.3 `tilt` —— **确认 0**

三次全 0。与「特写」同理（**推断**：`tilt` 在提示词里同样不存在）。

## 6. ★ 对 §18-A 与 §5 E5 的修法建议

> **总原则（由本轮实测直接推出）：**
> **「词不存在」⇒ 产出确定是 0（特写，实测 0/0/0）；
> 「词存在但无下限」⇒ 产出稳定非零（element，实测 8/9/7）。**
> ⇒ **两处该用完全不同的修法**，别当成同一类问题一起改。

### 6.1 §18-A 特写 —— **必须改提示词（不改 = 永远 0）**

**证据强度：实测 0（三次），且对照显示 LLM 会写 `zoom`（20/19/21 次）。**
⇒ **这是"教没教"的问题，不是"会不会"的问题。**

**★★ 而且"能不能用"这个问题已经有了明确答案：能用。**
消费侧（`placement.rs:174` + `fx.rs` 守卫 + 测试）**完整支持「特写」**，
⇒ **§18-A 是一处纯粹的提示词缺口，下游全部就绪**（详见下面「先补一条关键事实」）。

#### ★★ 先补一条本轮**顺带核到**的关键事实（它让修法变简单）

**消费侧早就完整支持「特写」** —— 我原以为要先核这一步，**核完发现它根本不是问题**：

| 证据 | 内容 |
|---|---|
| `crates/yekitrim-polish/src/process/placement.rs:174` | `pub const CLOSEUP_LABEL: &str = "特写";` —— **是独立档位** |
| `:172-173` 注释 | 「它与 `近` 是**两个独立档位**（**1.8 vs 1.5**），别把 `特写` 当成 `近` 的同义词 —— 手持摇摆仍然只允许 `近`」 |
| `crates/yekitrim-polish/src/process/fx.rs:359` | `if zoom.trim() != CLOSEUP_LABEL { … }` —— **消费代码在** |
| `fx.rs:3229-3315` | **§18-A 特写焦点守卫**的测试块（`cap_closeup_anchor` 改锚点、带空格的也要认） |
| `fx.rs:334-341` | 守卫语义完整：**特写强制 `anchor = liver`**（防"切了特写主播不见了"） |

⇒ **消费侧：代码 ✅ / 测试 ✅ / 语义 ✅ / 与 `近` 明确区分 ✅。**
**唯一缺的就是"提示词没教这个词"** —— 即 **§18-A 是纯粹的提示词缺口**，
**不存在"教了没人认"的风险**。

**建议**：
1. **★ 直接把「特写」加进 `segment.rs:83` 的枚举**（`"远"/"中"/"近"` → 加 `"特写"`）。
   这一处改完即可生效，**不需要动任何消费代码**。
2. **同时给一句"什么时候用"** —— 与现有四档 `style` 的写法同构
   （**实测证明那套写法有效**：四档里 LLM 用到了三档）。
   ⚠️ 必须**说清"特写 vs 近"**（1.8 vs 1.5、特写不继承手持摇摆）——
   `placement.rs:172` 已经写明了区别，**把它翻成给 LLM 看的语义**即可。
   不说清的后果是**推断**（依据 `segment.rs` E5 注释里作者自己的经验：
   「只教"有个 style 字段"的话, LLM 会**恒定用一个值**」）。
3. **给一个示例行**（与 camera 现有的 `例: {...}` 同构）。
4. ⚠️ **别只加词不加语义** —— 四档若缺区分说明，按上面那条经验会退化成"总是写同一个"。

**⇒ §18-A 属于"最便宜的一类修复"：单点改 1 行枚举 + 1 句语义 + 1 个示例，
且下游全部就绪。**

### 6.2 §5 E5 element —— **不需要加下限词**（但有两处值得改）

**实测：8/9/7 条、88% 的段都有 ⇒ "不产"的风险不存在。**
⇒ **给 element 加"必须/至少"是没必要的**，甚至有害（会加剧下面第 1 条）。

**真正该改的两处（均为实测/推断支撑）**：

1. **⚠️ 上限是"软"的，建议改成逐段硬约束。**
   实测每段 1~2 条，没有出现"整片大字"⇒ **现状尚可**；
   但提示词写的是"整段最多 1~2 条"，而**实测均值 1.6**、run1/run3 都有段顶到 2。
   **推断**：素材再"爆点密集"一些就可能超。
   ⇒ 若担心，改成"**每段**最多 1 条、**整片**最多 N 条"（把两个维度分开）。
   ⚠️ **本轮实测不足以证明现状是问题** —— 这是**预防性建议**，不是缺陷。

2. **★ 建议把 `kind="sticker"` 从 element 提示词里更明确地区分（或承认它不会被用）。**
   **实测：element 的 sticker 分支 0 次**，而独立 `type="sticker"` 17 次。
   ⇒ element 段落的 `kind` 实际只服务 `text`。**推断**：现有写法让人以为 element 是个"双分支"，
   但 LLM 一律走老路径。⇒ **要么简化 element 段落（只讲 text），要么显式说明何时该用
   `element+kind=sticker`**（若真有那个需求）。

3. **⚠️ 一个与提示词无关、但实测暴露的问题**：
   **温度 0 下三次段数不同（5/7/5）**。
   ⇒ **任何"改了提示词后数字变化"的验证，必须多跑几次取分布**，
   **单次对比会误判**（把随机波动当成改进或退化）。
   **建议**：把这条写进批 0.2 的验证方法里。
