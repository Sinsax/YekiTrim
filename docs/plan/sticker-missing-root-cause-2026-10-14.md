# 贴纸「某项目内不出现」真根因与修复（2026-10-14）

> 用户口径：「在某个项目内会有添加贴纸但是无法出现的问题，但是其他项目内更改贴纸位置时间、更换都是正常的」
> 方法：扫**全部真实工程（55 个 polish.toml / 131 个贴纸事件）** + **wasm 真渲染**，不是读源码猜。

## 二、★ 真根因：**四层缺陷叠在同一片段上**

### 2.1 ① 预览侧 `build_sticker_map` 不递归（**这是"一张都不出现"的直接原因**）

该片段的贴纸落在**带版本子目录**里：

```
assets/stickers/
└── ysyk_0.9.0/     ← 210 张 gif 全在这一层，顶层没有 ysyk.toml
```

`render/server.rs::build_sticker_map` **只扫顶层、且不筛扩展名**，实测算出**恰好 1 个键**：

```
"ysyk_0.9" -> "/assets/stickers/ysyk_0.9.0"     ← 一个**目录**被当成图片登记了
```

210 张真图**一张都没进映射** ⇒ 下游 `stickerSrc(name)` 查不到名字 ⇒ 恒返回 `''`
⇒ **预览里贴纸一张都不出现，且不报错**。这完全解释了用户的现象与
「其他项目正常」（它们目录是**扁平**的，顶层就有图）。

⚠️ `ServeDir` 的根是整个项目目录 ⇒ 子目录**本来就取得到**，坏的只有这张映射表。

### 2.2 ② `AssetDownloader::asset_map` 同一个 bug（第二份实现）

`assets/downloader.rs:370` 是**另一份**同名实现（注入到 config JSON），
老代码用 `unwrap_or(name)` ⇒ 目录名 `ysyk_0.9.0` 的 stem `ysyk_0.9` **照样被登记**。

### 2.3 ③ 转译器 `pickSticker` 恒取 `files[0]` ⇒ 5 张贴纸塌成 1 张

该片段 5 个事件的 tag 是「搞笑 / 震惊 / 爆笑 / 看热闹 / 笑」，
而 `STICKER_SYNONYMS` 把**其中 4 个映射到同一个库 tag**（`搞笑→笑`、`爆笑→笑`、`笑→笑`）
⇒ `files[0]` 反复取到同一张图。实测修前：

```
5 条 ssticker 轨 → 只有 **2 个素材**，其中 4 条轨画的是同一张
```

**用户看到的就是「贴纸没出现」** —— 那张图（`Popcat`/`拿勺子`）与他要的情绪毫无关系。

### 2.4 ④ 失败**静默**：`onStickerError` 不留痕

`PolishPreview.vue::onStickerError` 只往 `stickerFailed` 记一笔、**日志面板一个字都没有**
（而它的作用正是"回退到 emoji 兜底"）⇒ 分不清是「映射里没这个名字」还是「文件 404」。

## 三、修复（四处一起，不留分批）

| # | 文件 | 改法 |
|---|---|---|
| ① | `render/server.rs::build_sticker_map` | **递归**（显式栈，别用递归函数免得深目录爆栈）+ `is_image_file_name` 过滤 + URL 用**含子目录的相对路径** |
| ② | `assets/downloader.rs::asset_map` | 同口径（两处必须一致） |
| ③ | `tools/polish-to-dhampir.mjs` | 按**解析后的库 tag**（`picked.tag`）计数、在候选里**确定性分散**（序号取模，不用随机） |
| ④ | `PolishPreview.vue::onStickerError` | 记 `addClient('warn', …)`，把「哪个贴纸 / 哪个 URL / 该怎么办」写进日志面板 |

### 3.1 ⚠️ ③ 的第一版我写错过，必须留档

第一版按**原始** `sticker_tag` 计数。而原始 tag 各不相同
（`搞笑`/`爆笑`/`笑` 是三个不同的 key），各自从 0 开始 ⇒ 每个都取 `files[0]`
⇒ **等价于没改**（实测仍塌成 1 张）。**必须按 `picked.tag`（解析后的库 tag）计数。**

## 五、判据（**都能变异打红**）

| 判据 | 位置 | 变异自证 |
|---|---|---|
| 子目录布局必须建出映射 | `render/server.rs::sticker_map_scans_versioned_subdir` | 拿掉递归 ⇒ **红** |
| 递归是承重的 | `render/server.rs::sticker_map_recursion_is_load_bearing` | 同上 |
| N 个事件不许塌成一张图 | `scripts/check-yekitrim-translator.mjs` ㊲ | 退回 `files[0]` ⇒ **红**（实得 `甲,甲,甲`） |

⚠️ **㊲ 的判据是「不许全塌成一张」、不是「必须两两不同」** ——
候选只有 2 张时，3 个事件按序号取模必然是 A/B/A，那是**正确**行为。

## 七、给下一个接手的人的清单

1. **扫工程数据前先确认权威文件**（`polish.toml`，不是 checkpoint）。
2. **贴纸库有两种落盘布局**（扁平 / 带版本子目录）—— 任何"扫 `assets/stickers`"的代码
   都要问自己：**递归了吗？筛图片了吗？URL 带子目录了吗？**
3. **`files[0]` 是根因级反模式**：候选是多张时，恒取第一张 = "所有事件画同一张"，
   而且**报告里零差异**。
4. **静默失败要留痕**：`stickerFailed` 这类"回退到兜底"的机制，必须同时写日志面板，
   否则用户只能看到"东西没了"。

## 八、补充核查（2026-10-14 二轮）

### 8.1 ★ 两种布局**都真实存在**（我修的前提成立，且有旁证）

| 片段 | 图数 | 子目录 | 有 `ysyk.toml` |
|---|---|---|---|
| 不追星了…看热闹（**坏的那个**）| **210** | **1** | ✗ |
| clip-01 / clip-39 | 167 | 0 | ✓ |
| 其余 34 个 | 中位 **5** | 0 | 多数 ✗ |

⇒ **「扁平」是常态、「带版本子目录」是少数形态** —— 坏的那一个恰好是唯一一个
把整包（210 张）塞进子目录、且**没带 `ysyk.toml`** 的工程。这解释了
「**其他项目都正常，只有这一个坏**」，也解释了为什么它同时踩中两处缺陷
（① 映射只扫顶层；③ 拿不到 tag 索引 ⇒ `name` 全空）。

### 8.2 ⚠️ 纠正：`ysyk.toml` **不是** `name` 为空的判据

我一度以为「没 `ysyk.toml` ⇒ `Step2b` 跳过 ⇒ `name` 空」。**核对后不成立**：

- 好项目「排雷中」**也没有** `ysyk.toml`，但 4 个 `name` **全有值**；
- 唯一的差别是**复制进项目的图片集合**：好项目只放了**被选中的 4 张**（顶层），
  坏项目把**整包 210 张**塞进了子目录。

⇒ 所以「`name` 为空」与「映射坏掉」**不是两个独立缺陷，而是同一个来源**：
这个工程是拿**整包目录**（而不是"选中文件"）落盘的，于是
① 图片全在子目录里（映射扫不到）、② 没有为它建 tag 索引（`Step2b` 无候选）。

### 8.3 ⚠️ 纠正：底座的 TMP 报错**不是**缺陷（详见 §四 的重写）

我先前两条判断都错了，已在 §四 逐条纠正（文案准确、`issues` 去重是有意的、
系统 TMP 写不了是**环境属性**且底座已有注释明确按"环境限制、不是实现坏了"处理）。
