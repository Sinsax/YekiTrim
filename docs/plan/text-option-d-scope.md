## 〇、勘察结论：比预想的更好

**旋转的 GPU 实现已经存在、已经测试、两端同源** —— 文字只是**没走这条路**。

| 事实 | 证据 |
|---|---|
| `TransformV2.rotation` 字段存在 | `layer.rs:386`（`Layer.transform`） |
| `compose` 层**已经把 rotation 做成可动画的** | `compose.rs:350` `rotation_deg: animated(element.transform.rotation, "rotation")` |
| GPU 逆仿射**已实现**且注释详尽 | `render/compose.rs:281` `inverse_affine(...)`，含正/逆变换定义 |
| 已有单测覆盖 | `compose.rs:1141` / `:1196`（`rotation_deg == 30.0`）/ `render/compose.rs:691`（90°） |
| **文字路径完全不读 transform** | `text_overlay.rs` grep `transform\|rotation` = **0 命中** |

⇒ **不是"要发明一个新能力"，是"把已有能力接到文字上"。**

---

## 一、为什么文字漏了这条路（架构原因）

worker 出片每帧做**两件独立的事**：

```
① compose::evaluate_v2_with_assets(...)  → GPU 合成图层（走 transform / rotation / effects）
      ↓ readback 成 RGBA8 内存图
② painter.paint(&mut image, &overlay, ...) → CPU 把文字叠上去（不走 transform）
```

- ① 那侧 `inverse_affine` 已经把 `rotation_deg` 用上了
- ② 那侧 `TextOverlay { items, danmaku }` 里**根本没有 transform 字段**

⇒ **文字是在 GPU 合成之后、用 CPU 叠上去的**，所以图层的变换对它天然无效。
这不是 bug，是两条路当初的接缝。

---

## 二、⚠️ 一个必须先定的设计问题

`rotation` 在**两条不同的语义**上存在，接的时候要选一个：

| 接法 | 语义 | 影响面 | 风险 |
|---|---|---|---|
| **D1 · 轨级** | `TrackV2.subtitle` 旁边加一个 rotation | 整条字幕轨一起歪 | 小。但"倾斜 3 档"是**每档不同角度**，轨级做不到 |
| **D2 · 条级** | 每条文字（`TextItem`）带自己的 rotation | 每条字幕/每个文字元素各自的角度 | **推荐**。与 `dx_px`/`dy_px`/`color`/`font_px` 同款（都是"跟着条目走"） |

⚠️ 注意 `TextOverlay` 的注释已经立过规矩：

> ⚠️ **字幕与弹幕都没有帧级的"画法"字段了** —— 两者的轨道级样式都跟着**每一条**走。
> 理由是同一条真 bug 的**两处实例**：这里曾经有两个**共享槽**，循环里每轨整份重写、只留最后一份
> ⇒ **最后一条轨说了算**（元素轨 + 字幕轨并存时，前面那条轨的样式全失效）。

⇒ **必须走 D2（条级）**，否则会重蹈"共享槽"的覆辙。

## 九、⚠️ 阴影旋转中心：**这条已被推翻**（保留作为「实测推翻推理」的案例）

> **结论更正（2026-10-12，`replay` 实测推翻、我复核成立）：**
> **不做 `pivot`。阴影只传同一个 `transform`，偏移由既有 `origin + (dx,dy)` 表达。**
> 下面那段推理**是错的** —— 它假设"影子偏移应当跟着转"，但契约说 `shadow_dx_px` 是
> **文档/屏幕空间**的偏移（`overlay.rs:285`：*"文档像素，与 `transform.x/y` 同一坐标系"*）。
> **影子 = 同样的变换 + 屏幕空间固定平移 `(dx,dy)`** —— 光源方向固定，字转 90° 影子仍朝同一侧。
>
> **为什么"绕 pivot 转"表达不了那个诉求**（数值验算）：
> ```
> pivot=文字中心：rot=0 → 偏移 (0,0)；rot=90 → (0,0)   ← 中心与 pivot 重合，恒为零
> pivot=阴影中心：rot=0 → (8,0)；rot=90 → (0,8)
> ```
> pivot 是**旋转中心**，位图中心相对它的向量**本来就不该随旋转改变**。
>
> **正确断言（替换掉下面那条错的）**：
> | 测名 | 断言 |
> |---|---|
> | `阴影与文字用同一 transform ⇒ 影子做同样的旋转` | 带方向的字形，肉眼可区分 |
> | `阴影偏移是屏幕空间平移 ⇒ 旋转不改变偏移方向` | 写死容差 + 实测数字 |
>
> ⚠️ **但有一点仍然成立、不许一起删掉**：**影子必须跟着做相同的变换**
> （否则"字歪影子正"是真 bug）。**只是它的偏移方向不跟着转。**

### 以下为**已被推翻**的原推理（保留，勿据此施工）

**由 `replay` 勘察发现，我独立复核成立。** 这条不是"要不要转"，而是"**绕谁转**"。

### 三条实测事实

| # | 事实 | 位置 |
|---|---|---|
| 1 | 阴影位图**尺寸与文字不同**：四周各多一个 `pad` | `text_raster.rs:521-522` `width = text.width + 2*pad` |
| 2 | 阴影落点已含**扩边回挪 + 偏移** | `text_overlay.rs:712-713` `origin.x − pad + shadow.dx` |
| 3 | ⇒ 两张位图**中心不重合** | 推导见下 |

### 代数（我用 3 组数据验算过，含负偏移与 `dx=dy=0` 退化）

```
文字中心 = origin + (w/2, h/2)
阴影中心 = (origin − pad + dx) + ((w+2pad)/2, (h+2pad)/2)
        = origin + (w/2 + dx, h/2 + dy)
⇒ 阴影中心 ≡ 文字中心 + (dx, dy)          ← 正是"影子偏移"的语义
```

### ⚠️ 为什么这个坑特别阴

若直接对阴影位图调"**绕它自己中心转**"的仿射函数：
- 影子相对文字的那份 `(dx, dy)` **不跟着转**
- 症状：字歪了、影子仍往右下挪
- ⚠️ **而 `dx = dy = 0` 时完全看不出来** ⇒ **单测不造非零偏移就抓不到**

### 判据（必须钉住）

**阴影要绕「文字位图中心」转**，不是绕它自己的中心。
⇒ 实现上 `blit_affine` 必须**显式接收 `pivot`** —— 不能从位图尺寸推中心
（"从位图推中心"正是这个 bug 的来源）。

**两条配套断言**：

| 测名 | 断言 |
|---|---|
| `阴影偏移方向跟着文字一起转（dx/dy 非零时）` | `rot=90°` 且 `dx=+8,dy=0` ⇒ 影子中心的位移方向从 `(8,0)` 变到约 `(0,8)`（容差 ±1px） |
| `dx=dy=0 时绕文字中心与绕阴影中心结果相同` | 故意**钉住"为什么以前没人发现"**，防止后人删掉上一条时不知所以 |

### `paint_parts`（逐段 `.hl`）同理

它调 `paint_shadow` 传的是 **该段自己的文字起点**，紧随其后的 `blit_scaled` 用**同一个 origin**
⇒ **每段绕"该段自己的文字位图中心"**（逐段独立，与逐段栅格化一致）。
（该处注释 :596-597 说的"两端同序"是**层叠顺序**，与 pivot 无关 —— 已核实。）
